## (a) DSH plugin-API delta, 0.1.0-rc.7-era → 0.1.5-rc.1/rc.2

### a1. `ctx.web` seam (`WebSearchProvider` / `WebSearchRequest` / `WebSearchResult`): **unchanged**

Current shape (0.1.5-rc.2, `/home/jo/.npm/_npx/b86ed90107c62dab/node_modules/@deepseek-ai/dsh-web/lib/types/`):

- `types.d.ts:14-24` — `WebSearchRequest { query: string; maxResults?: number }`.
- `types.d.ts:32-39` — `WebSearchResult { content?: string; sources: readonly WebSearchSource[]; truncated: boolean }`.
- `types.d.ts:46-52` — `WebSearchSource { url; title?; snippet?; publishedAt? }` (only `url` required).
- `types.d.ts:98-104` — `WebSearchProvider { id: string; available(): boolean; search(request, signal?) }`, registered via `ctx.web.registerSearchProvider` (`index.d.ts:61`).
- `index.d.ts:24-29,42-48` — config `searchProvider`/`fetchProvider`; `$DSH_WEB_SEARCH_PROVIDER` feeds the *same* field, not a priority chain (`lib/index.js:48-57`).
- Selection semantics (`index.d.ts:33-41`, `lib/index.js:118-130`): configured id registered+available → it; configured+missing → `WEB_PROVIDER_CONFIGURED_MISSING`; configured+unavailable → `WEB_PROVIDER_CONFIGURED_UNAVAILABLE`; unconfigured: exactly one usable → auto-select, >1 usable → `WEB_PROVIDER_AMBIGUOUS`, 0 → `WEB_PROVIDER_UNAVAILABLE`. **Never registration-order dependent; multiple providers may coexist** (registry `Map` keyed by id; duplicate id → `WEB_DUPLICATE_PROVIDER`, `lib/index.js:80-84`). The seam itself truncates `sources` to `maxResults` and sets `truncated` (`lib/index.js:94-96`, `capSources`).

0.1.0-rc.7 comparison ([`packages/web/web/src/types.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.0-rc.7/packages/web/web/src/types.ts) and [`src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.0-rc.7/packages/web/web/src/index.ts) at tag `dsh-v0.1.0-rc.7`): a normalized diff of both files against the installed rc.2 build shows **only formatting differences plus one comment rewording** — every interface member, every selection rule, the env-var equivalence, `capSources`, and the error codes are identical. The branch's implementation (`origin/feat/dsh-web-search-router:packages/dsh-web-search-router/src/index.js:117-137`, provider id `'web-search-router'` from `src/router.js:12`) matches this contract exactly.

**Verdict: no breaking, no additive change on this seam. The spec's "External seam" and "Stock contract" decisions transfer verbatim.**

### a2. Credentials seam (`ctx.credentials`): reference half stable; **record half and event rename are new**

- rc.7 ([`packages/credentials/credentials/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.0-rc.7/packages/credentials/credentials/src/index.ts)): `CredentialProvider` had only the reference half — `resolve`/`describe`/`set`/`unset` — plus one event `credentials/updated` (`src/types.ts` at the same tag).
- Current (`…/@deepseek-ai/dsh-credentials/lib/types/index.d.ts:119-214`): the reference half is unchanged (`resolve(ref)` returns `{value, source}|undefined`, L121-129; `describe` returns `CredentialInfo {configured, source?, writable}` with no value slot, L134-136), and a **record half** was added: `CredentialKey` (`<scope>/<id>`), `readRecord`/`describeRecord`/`listRecords`/`modifyRecord`/`deleteRecord` (L154-191) — the "grant" store used by OAuth flows. Events were **renamed/split**: `credentials/updated` → `credentials/reference-updated`, plus new `credentials/record-updated` (`types.d.ts:68-94`). First-party doc: [`docs/subsystems/credentials.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/credentials.md).
- Key fact for the spec: `resolve` already **layers the process environment, the provider-managed store, and `.env` files** (`index.d.ts:103-110`), so a `resolve(EXA_API_KEY)` that misses is genuinely unconfigured — the branch's `process.env` fallback (`src/index.js:49-58`) duplicated a layer the seam owns and must not be rebuilt (matches the spec's Credential references decision). Ambient env changes are explicitly *not* observable as events (`types.d.ts:72-74`) — the spec's Further Notes already say this; it is correct against current source.
- Story 29 (settings/credential changes clear health) maps to `credentials/reference-updated(ref)` (`types.d.ts:82`) — a per-reference listener is the supported mechanism.

**Verdict: breaking only if you listened to `credentials/updated` (the branch did not); additive record half is an alternative home for OAuth grants but not required — see (b)2 for why the Codex hop does not need it.**

### a3. Settings + Settings card: **API moved from standalone function to service method; card slot confirmed current**

Writes gained `expectedRevision` conflict fencing (`update`/`replace`, L256-268) and a new `mutate(ns, ops, expectedRevision)` path-op write for redacted views (L280-282); `SettingsSectionHooks {setSource, onChange, validate?}` is unchanged in shape (L315-334). `redactSecrets` and `role('secret')` remain the redaction path (L12; `redact/redact.d.ts`).
- The browser Settings card is a real, current, first-party seam: the official cookbook ([`docs/cookbook/adding-a-settings-card.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-a-settings-card.md)) documents Host half `ctx.inject(['settings'], sctx => sctx.settings.installSection(...))` + browser half registering the **`settings.plugin.item`** slot with `ctx.settingsScope` revision-fenced writes, packaged as `./client` + `dsh.client` manifest. The slot is declared in `…/@deepseek-ai/dsh-client-ui-settings-plugins/lib/types/client/` (e.g. `AgentLoopCard.d.ts:5` uses `PropsRuntime<'settings.plugin.item'>`), and the installed `dsh-codex-connect` browser bundle actually registers `settings.plugin.item` (`/home/jo/.dsh/profiles/web/node_modules/dsh-codex-connect/lib/client.js`), proving the path works for a third-party plugin on 0.1.5-rc.x.

**Verdict: breaking rename for pre-0.1.2-era settings code (function→method, brand→plain string); additive `mutate`/revision fencing. Spec stories 3-4/34-35 and the "Settings UI" decision have a concrete, current, third-party-proven API.**

### a4. Patch loader (`- insert:` lists) and service injection: **unchanged**

## (b) `dsh-codex-connect` 0.1.0-alpha.4.34 public surface (the wrap target)

All citations: `/home/jo/.dsh/profiles/web/node_modules/dsh-codex-connect/` (installed 2026-09-11; `lib/index.d.ts` is the type contract, `lib/src-rxlwLWWN.js` the bundled implementation).

### b1. `OpenAICodexSearchProvider` — instantiable, per-request auth, fixed id

- Options (`lib/index.d.ts:509-529`, `OpenAICodexSearchProviderOptions`): `credentials: OpenAICodexCredentialStore` (required), `model`, `mode` (`'cached'|'indexed'|'live'`), `contextSize` (`'low'|'medium'|'high'`), `maxOutputTokens`, **`resolveRequestId: () => string` (required)**, and optional `proxyManager` / `resolveProxyUrl` / `recordRequest` (secret-free request recorder). Defaults exist as constants: `DEFAULT_OPENAI_CODEX_SEARCH_MODEL = "gpt-5.6-sol"`, mode/context-size/max-output constants (`lib/index.d.ts:424-430`).
- The class (`lib/index.d.ts:539-551`) implements `WebSearchProvider` with **hard-coded `id = "openai-codex"`** (`OPENAI_CODEX_SEARCH_PROVIDER`, L474) and an `available()` that checks only local config validity — credential presence is resolved per request (L546-547). It is stateless apart from its options: no store/transport/settings injection beyond the options object, no lifecycle to manage.
- Per-request behavior (bundle `src-rxlwLWWN.js:5142-5236`): caller `signal` honored throughout; an internal **30-second deadline** (`OPENAI_CODEX_SEARCH_TIMEOUT_MS = 3e4`, L5006) covering auth + body read; responses capped at 1 MiB (L5116-5131); POST to the fixed first-party endpoint `…/backend-api/codex/alpha/search` (`OPENAI_CODEX_SEARCH_URL`, `lib/index.d.ts:478`) with `authorization`, `chatgpt-account-id`, `originator: deepseek-harness` headers; result mapped by the exported `mapOpenAICodexSearchResponse` (L537) into the stock `WebSearchResult`.
- Mapping onto the spec's per-attempt needs: the router's codex adapter constructs it once (or per settings change) with `new OpenAICodexCredentialStore()` + resolved settings, delegates `search()`, and enforces the **router's 5 s attempt cap via the `signal` argument** (the provider combines the caller signal with its own 30 s deadline, so an earlier abort wins). `recordRequest` can feed the spec's content-free diagnostics. The fixed provider id never surfaces to `ctx.web` because the router never registers the wrapped provider (see (c)4).

### b2. `OpenAICodexCredentialStore` — the router can stop vendoring `codex-auth.js` entirely

- Public methods (`lib/index.d.ts:39-77`): `read(providerId)` (returns the **active** account's credential), `captureActiveAccount()` → `CapturedOpenAICodexAccount` (a snapshot `CredentialStore` whose `modify` refreshes **only the captured account and never changes the user's active selection**, L54-59 + bundle L886-905), `list()`, `accounts()` (browser-safe summaries), `accountIdForAccess(access)`, `activate(accountKey)` (account switch), `removeAccount`, `modify(providerId, fn, options?)` (serialized read-modify-write under the writer lock, with a 15 s refresh allowance, L75-76), `delete`. Constructor takes an optional explicit path, defaulting under `$DSH_HOME` (`openAICodexAuthPath()`, L37,45).
- Document format (`src-rxlwLWWN.js:770-830`): `AUTH_FORMAT_VERSION = 2` (L715) — `{version: 2, activeAccountId, credentials[]}` with ≤16 accounts, duplicate-`accountId` and active-must-exist invariants; **version-1 documents are still accepted on read** (`{version:1, credential}`, L778-784) and the first v1→v2 write creates a one-time owner-only rollback copy `<file>.v1-backup` (`OPENAI_CODEX_AUTH_V1_BACKUP_SUFFIX`, `lib/index.d.ts:19`; write path L867-880, `mode 0o600`/`dirMode 0o700`).
- The live shared document is now version 2 (`/home/jo/.dsh/.openai-codex-auth.json`: keys `version,activeAccountId,credentials`, `version: 2` — structure only inspected, no values). The branch's vendored reader is strict version-1-only (`origin/feat/…/src/codex-auth.js:29` `AUTH_FORMAT_VERSION = 1`; L64 throws `unsupported format version` for anything else), so on this machine its `hasCredential()` swallows the throw and returns `false` — **the branch's Codex hop is silently dead, and any fresh implementation must obtain auth through this store, not a vendored parser.**

### b3. `OpenAICodexTransport` / `OpenAICodexTransportError` — a good contract, but **not what search throws**

- The structured contract (`lib/index.d.ts:151-179`): 12 stable codes (`OPENAI_CODEX_TRANSPORT_ERROR_CODES`: `invalidRequest`, `signedOut`, `reauthRequired`, `rateLimited`, `upstreamRejected`, `upstreamUnavailable`, `redirectRejected`, `timeout`, `canceled`, `networkError`, `responseTooLarge`, `malformedResponse`), `OpenAICodexTransportError { code, status?, retryAfterSeconds? }`, and the structural predicate `isOpenAICodexTransportError(error)` that avoids cross-package class identity. The transport service (`OPENAI_CODEX_TRANSPORT_SERVICE = "openaiCodexTransport"`, apiVersion 1, L136-138,206-215) maps HTTP 429 → `retryAfterSeconds` from `Retry-After` (bundle L4701-4710).
- However, `OpenAICodexSearchProvider.search()` does **not** use that transport: it throws `WebError` — `WEB_PROVIDER_CREDENTIAL_MISSING` for missing credentials and for HTTP 401/403, `WEB_PROVIDER_ERROR` for every other failure **including 429**, with the HTTP status present only in the message text (bundle L5218-5229). `WebError` comes from `@deepseek-ai/dsh-web` (same class the router already translates).
- Consequence for the spec's failure taxonomy: the codex adapter can classify `WEB_PROVIDER_CREDENTIAL_MISSING` → `auth` and signed-out vs reauth via the message, but a 429 currently arrives as `WEB_PROVIDER_ERROR (HTTP 429)` with **no machine-readable `Retry-After`** — story 26 cannot be satisfied for the Codex hop by wrapping this provider as-is (see amendments).

### b4. Compatibility machinery — reusable as a gate

`lib/index.d.ts:225-289` + `compatibility.json`: `COMPATIBILITY_SCHEMA_VERSION = 1`; `SUPPORTED_DSH_PLUGIN_API_VERSIONS = ["0.1.2-rc.1","0.1.5-alpha.1","0.1.5-rc.1","0.1.5-rc.2"]` across a 14-package `DSH_PLUGIN_API_PACKAGES` list (includes `dsh-web`, `dsh-settings`, `dsh-atomic-write`, `dsh-home-paths`, `dsh-llm-pi-ai`); `SUPPORTED_PI_AI_RANGE = "^0.84.2 || 0.85.1"`; `COMPATIBILITY_CONTRACT` mirrors `compatibility.json` as typed data; `evaluateCompatibility(input)` / alias `assessCompatibility` are **pure functions over supplied versions** (no filesystem), `detectCompatibility` reads installed metadata. Statuses are honest: `compatible | unverified | incompatible | unknown` ("Version metadata proves a declared match, not behavioral failure", L236). The router can import `assessCompatibility`/`isSupportedDshPluginApiVersion` (both exported, bundle export map) as its own compatibility gate for the Codex hop, or replicate the pattern.

### b5. Versioning / migration — alpha cadence is the dependency risk

- `VERSIONING.md`: releases are an independent `0.1.0-alpha.4.x` counter; in the `0.y.z` period **incompatible changes are permitted with explicit release notes and migration guidance**; verified exact DSH×plugin pairs live in a `verified-compatibility.json` catalog ("Keep … at the existing URL", L26 — the file itself is not in the repo root contents listing on `main`, so its hosted location was not verified here); published packages are never overwritten; `alpha` dist-tag is explicitly "not a compatibility guarantee" (`README.md`).
- Cadence: 40 releases between 2026-08-14 and 2026-09-11 ([`gh release list`](https://github.com/franksong2702/dsh-codex-connect/releases)) — roughly daily; the installed `.34` was already superseded by `.35` within hours.
- Concrete host-break precedent: Alpha 4.33 fails on DSH `0.1.5-rc.1` with a model-index crash; fixed in `.34` via [issue #178](https://github.com/franksong2702/dsh-codex-connect/issues/178) (`docs/reference.md:119`). A DSH bump can therefore break the plugin between plugin releases.
- `MIGRATION.md`: `dsh-codex` and `dsh-codex-connect` **cannot be active together** (same provider id `openai-codex`, same OAuth filename, same Cordis row `llm-openai-codex`); after migration `enableSearch`/`enableImageTool`/etc. default to `false`, and the prior `web.searchProvider` selection is deliberately *not* preserved (L8-9).

### b6. Is `lib/index.d.ts` a stable contract?

No explicit promise: `VERSIONING.md` defines the plugin's "public behavior" as "configuration, tools, commands, and stored data" — TS exports are not named. Empirically the declared export set is identical between installed `0.1.0-alpha.4.34` and `main` (= `.35`, `lib/index.d.ts` 779 lines; a declared-name diff is empty). `package.json` `peerDependencies` pin DSH packages by **exact version enumeration** (`"0.1.2-rc.1 || 0.1.5-alpha.1 || 0.1.5-rc.1 || 0.1.5-rc.2"`), not ranges — the safest peer strategy for a wrapper is to mirror that enumeration or pin an exact plugin version, not a caret range over an alpha series.

## (c) Seam composition: codex-connect vs an external router on `ctx.web`

### c1. Does codex-connect register a WebSearchProvider by default? **No.**

Its bundle patch inserts the row with every optional capability off: `cordis.patch.yml` → `- insert: llm-openai-codex … enableSearch: false, enableImageTool: false, …` ("Install the provider without changing the profile's current default model or web-search route"). `Config` schema default confirms `enableSearch: z.boolean().default(false)` (bundle L6345). Only when the resolved setting is `true` does `apply()`'s reconciler spawn a sub-fiber that constructs `OpenAICodexSearchProvider` and calls `webCtx.web.registerSearchProvider(provider)` (bundle L6406-6431). `OPENAI_CODEX_SEARCH_PROVIDER = "openai-codex"` is the **WebSearchProvider id string** (`lib/index.d.ts:473-474`, "Stable dsh web-provider id selected by the bundle patch"); it is a different thing from the settings namespace (`llm-openai-codex`, L403) and coincides textually with the pi-ai LLM provider id (`OPENAI_CODEX_PROVIDER`, L11).

### c2. Route resolution when both are present

- The profile pins the route at the composition layer: `- id: web / config: searchProvider: web-search-router` (`/home/jo/.dsh/profiles/web/cordis.patch.yml`; the patch layer applies after all bundle layers, so it beats any bundle's own pin). `WebRuntime` reads that config once at construction (`dsh-web/lib/index.js:53-57`). Both providers may be *registered* simultaneously; selection is by configured id, and ambiguity (`WEB_PROVIDER_AMBIGUOUS`) only arises when **nothing** is configured and >1 provider is usable — never registration order (`index.d.ts:33-41`).
- If the user then flips codex-connect's `enableSearch` on, the plugin does not merely register — it **takes over the route at runtime**: `selectOpenAICodexSearchRoute` writes the `WebRuntime`'s private `searchProviderId` field via `Reflect.set` (bundle L6042-6068), because DSH exposes no writable `web` settings namespace (documented in `docs/agent-notes/search-route-runtime-override.md`: on 0.1.2-rc.1 — and still true on 0.1.5-rc.2, see a3 — "DSH … keeps the WebRuntime provider selection in its initial plugin config and does not register a `web` settings namespace"). Disabling restores the previously selected id, but only if no third-party changed it meanwhile; the README states the user-visible contract: "Codex Search … Selects Codex for the entire profile's search route; disabling restores the previously active route." The router stays registered but unserved while that override is active.
- Practical consequence: with the router installed, codex-connect's `enableSearch` must stay `false`, and the router's README/profile patch should say so — otherwise the router silently stops serving `web_search`.

### c3. What `assertNoOpenAICodexProviderConflict` guards

The **pi-ai LLM provider registry, not the web seam**: `apply()` calls it with `ctx.llm.listProviders().map(p => p.id)` (bundle L6386) and it throws an actionable migration message when the legacy `dsh-codex` bundle (or a manual `openai-codex` provider row) already owns that id (`lib/index.d.ts:328-331`). It has nothing to do with `ctx.web` provider ids.

### c4. Wrap vs compose — recommendation for the fresh PR

Two viable shapes, judged against the spec's own constraints ([issue #8](https://github.com/S2P2/dsh-lab/issues/8) Implementation Decisions: "the Router is the only `WebSearchProvider` registered … It does not receive or recursively call the `ctx.web` search seam"):

1. **Compose via the seam** — leave codex-connect's provider registered (`enableSearch: true`) and have the router call it. **Rejected**: it violates the no-recursion decision (the router would have to call `ctx.web.search()` or reach through the runtime's private registry), and c2 shows codex-connect would fight the router for the route selection.
2. **Wrap the public exports as a library dependency** — the router's codex adapter imports `dsh-codex-connect` root, constructs `new OpenAICodexCredentialStore()` (same default `$DSH_HOME/.openai-codex-auth.json` — the MIGRATION.md shared-document guarantee) and `new OpenAICodexSearchProvider({credentials, model, mode, contextSize, maxOutputTokens, resolveRequestId, …})`, and never registers it on `ctx.web`. `enableSearch` stays `false` in the profile. This is the same pattern the 2026-08 prior-art note recommended for `dsh-codex` (§4: "Importing the package root does not itself require invoking its Cordis `apply()`"), re-targeted to the package that actually owns the live v2 credential document. Importing the root triggers no Cordis effects (`apply` is only called by the loader for the `llm-openai-codex` row), and `mapOpenAICodexSearchResponse` / `OPENAI_CODEX_SEARCH_URL` / settings constants are exported for adapter reuse.

**Recommendation: option 2**, with a peer-dependency strategy from b6 (exact enumerated versions or an exact pin), a startup compatibility check reusing `assessCompatibility` (b4), and a README/profile note that codex-connect's `enableSearch` must remain off (c2). License: Apache-2.0 (`package.json`, `LICENSE`, `NOTICE`) — depending on the package is cleaner than copying; preserve attribution if any source is copied.
