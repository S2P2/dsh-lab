# Hermes Agent profile: architecture & capability surface

**Verdict.** Hermes Agent (NousResearch, MIT, Python) is the inverse of DSH's bet: instead of an orthogonal plugin kernel with no privileged capabilities, it ships one fat, deliberately productized singleton — a synchronous `AIAgent` conversation loop (`run_agent.py`, ~8.4k lines; CLI is ~19.5k; SQLite state store ~13k) — and builds every headline capability directly into or around it. Its thesis is *persistent, self-improving agency*: bounded agent-written memory files, a skills library the agent authors and refines itself, a post-turn background review fork that writes lessons straight to durable stores, a curator that maintains the skill collection, and per-chat sessions reachable from ~22 messaging platforms, cron jobs, a desktop app, and an OpenAI-compatible API server. Composition exists but is *enumerated*, not universal: there are specific provider-plugin kinds (platforms, memory providers, context engines, browser providers, dashboard plugins) plus a giant shared `config.yaml` — no uniform "everything is a swappable row" kernel. Compared to DSH, the material deltas concentrate in D7 (memory/learning — everything DSH deliberately lacks), D9/D10 (cron + chat channels as first-class), and operational surface (dashboard auth gate, egress proxy); while DSH remains ahead on composition orthogonality, event-sourced traceability, guarded tool pipeline, OS sandbox runners, and model-authored orchestration (workflow/Ralph/goals), none of which Hermes has.

## 1. Positioning

README: "**The self-improving AI agent built by Nous Research** … the only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, and builds a deepening model of who you are across sessions" (`README.md`). Product page adds the RL framing: batch trajectory generation + trajectory compression "for training the next generation of tool-calling models" (`batch_runner.py`, `trajectory_compressor.py`, `datagen-config-examples/{web_research.yaml,trajectory_compression.yaml,browser_tasks}`). Install = `curl … install.sh | bash` (also `.ps1`; Termux extra supported), run anywhere "$5 VPS → GPU cluster". Single-user personal-agent category — closest sibling OpenClaw, with a documented migration path (`hermes claw migrate`, imports SOUL.md/memories/skills/allowlists).

## 2. Runtime core: one class, many doors

- **Platform-agnostic singleton**: "One `AIAgent` class serves CLI, gateway, ACP, batch, and API server. Platform differences live in the entry point" (docs Architecture §Design Principles; `run_agent.py:421 class AIAgent`). Data flow per door: `HermesCLI.process_input()` / gateway `_handle_message()` / scheduler tick each construct or reuse an `AIAgent` with session history loaded from `SessionDB`.
- **Loop**: turn lifecycle = build/reuse cached system prompt → preflight compression check (>50% context) → format messages for one of three API modes (`chat_completions` / `codex_responses` / `anthropic_messages`) → inject ephemeral layers (budget warnings) → Anthropic cache breakpoints → interruptible call (`_interruptible_api_call`: HTTP in background thread; user input/`/stop` abandons it, nothing partial enters history) → tool_calls executed (single inline; multiple via `ThreadPoolExecutor`, results reinserted in call order) → loop (docs Agent Loop Internals; enforced strict role alternation `Assistant→Tool…→Assistant`).
- **Budgets/fallback**: `IterationBudget` default 90 iterations (`agent.max_turns`); subagents capped independently (`delegation.max_iterations` default 50). Fallback chain `fallback_providers` on 429/5xx/401 (credential refresh before failover); auxiliary tasks (vision, compression, web extract) have independent fallback chains under `auxiliary.*`.
- **Persistence**: after each turn messages append to SQLite (`hermes_state.py`, schema in `hermes_state_schema.py`; FTS5 availability-probed with graceful degradation `:148–156`), memory flushed, resumable via `/resume`. No append-only raw-chunk event log, no replay invariant; history lives as message rows.
- **Prompt discipline**: tiers `stable → context → volatile` (`agent/prompt_builder.py`, `system_prompt.py`); "prompt stability — system prompt doesn't change mid-conversation; no cache-breaking mutations except explicit user actions (`/model`)" is a stated design principle. Mid-session context arrives via **lazy subdirectory hints**: `agent/subdirectory_hints.py` appends discovered project files (AGENTS.md, CLAUDE.md, .cursorrules — also loaded at startup from CWD) to *tool results*, never the system prompt, explicitly "preserving prompt caching".
- **Context compression**: trigger at >50% context (preflight) / >85% (gateway auto); flush memory first, summarize middle turns, keep last N (`compression.protect_last_n` default 20) intact, keep tool pairs together, and mint a **new child session id** ("session lineage") — compaction creates a successor session rather than mutating one log (`run_agent.py` loop + `agent/context_compressor.py`, `conversation_compression.py`; docs Context Compression page).
- **Profiles**: `-p name` swaps whole `HERMES_HOME` (config/memory/sessions/gateway PID/concurrent instances) — `hermes_constants.py`.

## 3. The learning loop (headline dimension)

This is where Hermes materially diverges from DSH, which records D7 as absent-by-scope.

- **Bounded declarative memory** — `MEMORY.md` (~2,200 chars) + `USER.md` (~1,375 chars) injected into the volatile prompt tier; agent writes via a `memory` tool (agent-level intercepted in `run_agent.py`), consolidates when full; frozen snapshot semantics: written immediately, visible to prompts next session (docs Configuration/Tips; gate key `memory.write_approval`).
- **MemoryManager + provider seam** — `agent/memory_manager.py`: single integration point; built-in files are internal providers; **at most one external plugin provider** runs at a time (schema-bloat rationale). Provider contract (`agent/memory_provider.py`): `initialize / system_prompt_block / prefetch(query)` before each turn `/ sync_turn(user, asst)` after / `get_tool_schemas / handle_tool_call / shutdown`, optional hooks `on_turn_start, on_session_end, on_session_switch, on_pre_compress(v2 checkpoint contract), on_memory_write, on_delegation, backup_paths`. Eight first-party provider plugins ship: `plugins/memory/{honcho,hindsight,mem0,supermemory,byterover,holographic,openviking,retaindb}` (Honcho = dialectic user modeling per README). A deterministic "memory was used" indicator glyph per provider (`RecallStatus`) surfaces recall provenance in replies.
- **Agent-managed skills** — `tools/skill_manager_tool.py`: actions `create/edit/patch/delete/write_file/remove_file`; SKILL.md bundles under `~/.hermes/skills/` (bundled packs under `skills/<category>/`, optional catalog under `optional-skills/`, hub-installed flagged). Progressive disclosure: list name+description → `skill_view` loads full content + linked references/templates/scripts. Skill metadata standard incl. version/license/platforms (agentskills.io compatible). Slash-command invocation (`/deploy-staging`) and message-trigger activation.
- **Background self-improvement review** — `agent/background_review.py` (docstring verified): *"After every turn, `AIAgent.run_conversation` may call `spawn_background_review` to fire off a daemon thread that replays the conversation snapshot in a forked `AIAgent` and asks itself 'should any skill/memory be saved or updated?'. Writes go straight to the memory + skill stores. Main conversation and prompt cache are never touched."* Fork inherits live runtime (provider/model/base_url/credentials/cached system prompt → same prefix cache); tool whitelist limited to memory+skill tools. On messaging platforms its writes **stage for human approval**; CLI can prompt inline. Config: `auxiliary.background_review.enabled: false`; manual alternative `/refine` (`run_agent.py:1883–1934`).
- **Curator** — `agent/curator.py`: inactivity-triggered (not cron) background maintenance fork over **agent-created skills only**: lifecycle transitions, pin/archive/consolidate/**patch**; "never auto-deletes — only archives. Archive is recoverable"; state in `.curator_state`.
- **Human gates on learning** — `skills.write_approval` / `memory.write_approval`: writes staged under `~/.hermes/pending/{skills,memory}/`, reviewed via `/skills pending|diff <id>|approve|reject`, `/memory …`, toggleable live (`config_defaults.py`; docs Configuration; slash commands reference). Consent-aware learning is an explicit design axis.
- **Learning-journey graph** — `agent/learning_graph*.py`: nodes = saved skills + `memory:<source>:<index>` chunks; rendered as CLI timeline, TUI overlay `/journey`, desktop Star Map panel; supports prune (`delete`)/edit of individual learned items.
- **Conversational retrieval** — `session_search`: FTS5-backed discovery/scroll/read/browse shapes returning actual DB messages without LLM calls (tools-reference); cross-session recall described as "FTS5 session search with LLM summarization" (README). Plus per-chat gateway history loading.

## 4. Tools, execution, safety

- **Registry**: import-time registration — any `tools/*.py` with top-level `registry.register()` is auto-discovered; `model_tools.py` collects schemas/dispatches; `toolsets.py` groups tools into sets enabled per platform (cli/tui/gateway/api_server/acp…). `/tools disable` removes from toolset + resets session. 60+ built-ins (tools-reference) across web/search/terminal/file/browser/vision/image_gen/tts/todo/memory/session_search/cronjob/code_execution/process…
- **Terminal + seven execution backends** (`tools/environments/`): `local, docker, ssh, singularity, modal (+managed_modal), daytona, vercel_sandbox`; `file_sync.py` for remote FS. README marketing emphasizes serverless persistence (Daytona/Vercel "hibernate when idle"). Working-directory allowlist validation ("input sanitization") guards terminal cwd (docs Security layer 8). Background processes: `terminal(background=true)` + `process` tool (list/poll/log/wait/kill/write) with `notify_on_complete` auto-notification.
- **Approval**: `tools/approval.py` (~6.8k lines) — dangerous-command pattern classification; `approval_callback` prompts (CLI inline sudo-style, platform approve buttons); `HERMES_YOLO_MODE` env frozen at import + config `approvals.mode/yolo` + cron approve-mode (`approval.py:34–37,360,436`). File-write denylist + optional write sandbox (`agent/file_safety.py`). **Context-file threat scanning** scans AGENTS.md-class inputs for prompt injection using a threat-pattern library with scopes (`prompt_builder.py:64–80`). Cross-session isolation + hardened cron paths (docs Security eight layers).
- **Egress proxy** — `agent/proxy_sources/iron_proxy.py` (+ docs Egress internals): network egress control layer, bind-host liveness probing nuance documented.
- **Browser control** — CDP attach to a running Chromium-family browser (`/browser connect`, default 127.0.0.1:9222; auto-launch if none): `browser_tool.py` (~256KB), `browser_cdp_tool.py`, supervisor + extension router; separately `tools/computer_use/` (CUA backend, vision routing, permissions, doctor) for Linux desktop control; `plugins/browser/` dashboard plugin; Browser Use cloud backend via Nous Portal Tool Gateway.
- **Code execution (PTC)** — `tools/code_execution_tool.py` docstring: LLM writes a Python script calling Hermes tools via RPC (local = UDS stub module + listener thread; remote = file-based RPC shipped to the environment), collapsing multi-step chains into one inference turn. ("Zero-context-cost pipelines.")

## 5. MCP / protocols

- **MCP client, deep**: `tools/mcp_tool.py` + oauth managers (`mcp_oauth*`, CIMD tests), schema cache TTL, stdio watchdog, circuit breaker, trust gating, elicitation, SSE/streamable-http transports, cross-process discovery (~100 test files under `tests/tools/test_mcp_*`). Docs describe connecting servers, filtering tools, credential env-var isolation for MCP subprocesses.
- **Tool Search bridge**: when activated, MCP/plugin tools collapse into three bridge tools; per-tool schemas load on demand (docs Tool Search) — token-economy mechanism for large catalogs.
- **Hermes as MCP server** (`mcp_serve.py`, `agent/transports/hermes_tools_mcp_server.py`): exposes messaging conversations as MCP tools — 9-tool surface matched to OpenClaw's bridge (`conversations_list/get, messages_read, attachments_fetch, events_poll/wait, messages_send, permissions_list_open/respond`) + `channels_list`. Other agents (Claude Code/Cursor/Codex) become remote operators of your messaging agent.
- **ACP adapter** (`acp_adapter/`, 7 modules): wraps synchronous AIAgent in async JSON-RPC stdio server; sessions new/load/resume/fork/list/cancel; per-session model switch; permission bridge adapts dangerous-terminal approvals into ACP requests (docs ACP Internals).
- **API server** (`gateway/platforms/api_server.py` + docs): OpenAI-compatible `/v1/chat/completions`, `/v1/responses`, `/v1/runs`; capability discovery `/v1/capabilities`; read-only `/v1/skills` + `/v1/toolsets` enumeration gated by `API_SERVER_KEY`; stable long-term-memory scoping header `X-Hermes-Session-Key` distinct from transcript-scoped `X-Hermes-Session-Id`.
- **A2A** agent-to-agent exposure (messaging/a2a docs; bearer token + explicit `A2A_HOST`).

## 6. Delegation & parallelism

- `tools/delegate_tool.py`: spawns child `AIAgent`s — fresh conversation (no parent history), own task_id/terminal session/file-ops cache, parent's toolsets minus child-blocked tools, focused prompt; parent sees only delegation call + summary result. Single and batch-parallel modes; orchestrator children wait on their workers to synthesize.
- `tools/async_delegation.py`: `delegate_task(background=true)` → daemon-executor handle immediately; completion events land on a shared `process_registry.completion_queue`; CLI/gateway drain it while idle and **forge a fresh user/internal turn** — completions never splice between a tool result and assistant message (alternation preserved).
- Iteration budgets per child (default 50) atop parent budget. Multi-agent board: `plugins/kanban` dashboard plugin with watchers feeding lanes (`gateway/kanban_watchers.py`); human-oriented visualization rather than a model-facing orchestration engine (no workflow-script language, goal rounds, or team DAG concepts found anywhere in-tree).

## 7. Gateway, cron, bot mode

- **Gateway**: single long-running process unifying all channels; core platform adapters in `gateway/platforms/` (signal, whatsapp_cloud/common, bluebubbles/iMessage, weixin/wechat, yuanbao, qqbot, webhook, email, api_server…) and ~21 more as platform plugins (`plugins/platforms/`: telegram, discord, slack, teams, matrix, mattermost, feishu/lark, dingtalk, line, ntfy, homeassistant, google_chat, sms, irc, simplex, a2a, buzz, photon, raft, wecom…) → **20+ total surfaces**, threads/reactions/typing/streaming per-platform matrix (docs Messaging). Authz mixin + DM pairing (`gateway/authz_mixin.py`, `pairing.py`); channel directory resolves friendly names; voice memos transcribed; cross-platform conversation continuity (`relay/`).
- **Cron**: `cron/jobs.py` — `~/.hermes/cron/jobs.json` (per-profile), cross-process advisory file locking; scheduler tick loads due jobs → fresh no-history AIAgent → inject attached skills as context → deliver to target (`platform[:chat][:thread]`, resolved at fire time; fan-out lists supported). Schedule syntax: interval/every, full cron expr, one-shot delay (`"30m"`). Script-only no-LLM jobs. Runs ledger with attempt states claimed→running→terminal completed/failed/unknown; post-restart ownership proof by PID+fingerprint; unknown attempts audit-only, never re-run (docs Cron Internals). Delivery targets = every gateway platform + `origin` + `local`; thread-preferred continuation opens per-run threads on Telegram topics/Discord/Slack threads, mirrors into DMs otherwise (`mirror_delivery`/`in_channel`); `[SILENT]` response convention suppresses delivery. Webhook triggers (GitHub templates), natural-language scheduling via `cronjob` tool; scheduled agents may manage their own table.
- **Bot Mode**: named bots, each with own model/memory/skills/routines/chats; group chats with `@mentions`; routine loops ("drive") with settlement mechanics (recent commit `#94478` labels "cap-forced drive exits" vs "consensus settle"); probes and failure reasons tracked (`tools/bot_mode_dm.py`, `bot_mode_probe.py`, `bot_relay.py`, `bot_failure_reasons.py`).

- **Providers**: resolver maps `(provider, model) → (api_mode, api_key, base_url)` shared by every entrypoint (`hermes_cli/runtime_provider.py`); adapters incl. anthropic (direct+OAuth), codex responses/runtime, bedrock, vertex, gemini-native, azure identity, LM Studio reasoning, moonshot schema, copilot-ACP client (agent/ dir); 18+ providers claim in docs. Aux registries give vision/image-gen/video-gen/TTS/transcription/web-search each a registry+routing seam (`web_search_registry.py`, `tts_registry.py`, …) with independent fallback chains. Credential pool/rotation (`credential_pool.py`, `credential_sources.py`, `secret_scope.py`, redact). Nous Portal = commercial bundling of models + Tool Gateway backends (Firecrawl search, FAL image, OpenAI TTS, Browser Use cloud browser).
- **Entry surfaces**: interactive CLI REPL; full TUI (`ui-tui/` + `tui_gateway/server.py` as the local RPC/WebSocket compute host behind CLI *and* dashboard *and* Desktop); `hermes serve/dashboard` (port 9119); Electron desktop app (`apps/desktop`, `main: dist/electron-main.mjs`) attaching to local or remote dashboards; voice mode (CLI mic, platform voice notes, Discord voice channels); batch runner; Python library usage.
- **Deployment/security posture**: secrets in `~/.hermes/.env` (0600); Docker images w/ June-2026 hardening ("unauthenticated public dashboard was the entry point for the June 2026 MCP-config persistence campaign — internet scanners … planting an SSH-key backdoor", docs Docker); **dashboard auth gate engages iff bind is non-loopback**, three providers (username/password basic, Nous Portal OAuth, self-hosted OIDC), fail-closed, `--insecure` now a no-op; peer-IP + Host-header (DNS-rebinding) guards on the WebSocket; systemd/SSH-tunnel guidance; plugins directory layout is additionally designed around the incident (`plugins/dashboard_auth/`).
- **Dashboard plugins SDK** (`developer-guide/desktop-plugin-sdk.md`, `plugins/` tree): dashboard tabs/plugins served under `/api/plugins/` with REST routes reading config via `GET /config`; kanban shows tenant filters + lane-by-profile defaults.

## 10. Absence is data (both directions)

**DSH has, Hermes lacks:** uniform plugin kernel w/ reversible-effect composition and config-layering; generated capability-seam completeness guarantees; append-only raw event log ("model-visible ⇒ logged") powering trajectory/replay/search/invariants; runtime invariants subsystem; monotonic guarded tool pipeline w/ frozen arguments; OS-confinement sandbox runners incl. honest `full`/`partial` enforcement reporting; fail-closed sandbox-unavailable refusal; model-authored dynamic packages/orchestration (Creator equivalents: none — no workflow scripts, no Ralph, no goal model, no team DAG); plan mode; KV-cache-purist tool-catalog constancy (Hermes prefers tiered staleness instead); flat scope/shadowing registration.

**Hermes has, DSH lacks:** any persistent/learned state (memory files, learned skills, curated user model) incl. consent gates; automatic experience-consolidation daemons; chat platforms, cron-with-delivery, bots/routines, voice; browser/computer control; egress proxy; executable-catalog security scanning of instructions; serverless execution backends; human-readable sessions store w/ portability export; dashboard authentication providers; commercial one-subscription tool bundling (Portal) as adoption lubricant; training-data factory surface (batch trajectories, compressor, RL framing) as a *stated purpose of the harness itself*.
