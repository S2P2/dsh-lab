# nanobot (HKUDS): flattened personal-agent runtime architecture & capability surface

**Baseline for:** Agent Harness Capability Map (profile #8 of 18)

**Verdict.** nanobot is OpenClaw's product instincts flattened into directory-scanned Python: one process, one `config.json`, one workspace directory — chat channels (17 packages: Telegram, Discord, Slack, WeChat/WeCom, Feishu, QQ/NapCat, DingTalk, Matrix, Mattermost, MS Teams, Signal, Email, WhatsApp, WebSocket/WebUI), cron+heartbeat scheduling, Markdown persona files (`SOUL.md`/`USER.md`), and a two-stage memory pipeline (Consolidator → cron-driven "Dream" consolidation with **git-versioned memory edits**). The core really is small — bus 645 LOC, cron 1.2k, gateway 889, api 491 — but the *system* is not: ≈99k Python LOC excl. tests (≈129k incl. per-channel tests), with channel breadth alone ≈52k. Its extension model is the anti-Cordis: no service kernel, no seams — channels are self-discovered packages scanned from `nanobot/channels/`, tools are classes found by pkgutil (+ one `nanobot.tools` entry-point group), providers are rows in one registry file. MCP is deliberately pushed *outside* the loop (caller-owned `MCPProvider` lifecycle; the loop just receives a `ToolRegistry`), and v0.3's sustained-goal model converges on DSH's to a striking degree: `/goal` objectives, bounded invisible continuation turns (cap 12), even an `update_goal action='complete'` instruction. For DSH the reveal is: nanobot productizes the four things DSH deliberately left absent (chat channels, memory, cron, persona) as *flat packages + files*, not seams — evidence that those capabilities can be packaged much more cheaply than DSH's seam grammar implies, at the cost of zero config-layered composition, no approval/sandbox story, and auditability moved out of the log and into artifacts (git-committed memory edits, `/context` inspection) instead.

## Architecture profile

### 1. Runtime shape & loop (D1)
- Two entry paths off one loop: `nanobot agent -m "…"` (one message → reply in terminal) and `nanobot gateway` (long-running: channels + WebSocket/WebUI + workspace-scoped cron + system jobs Dream/heartbeat + health endpoint `127.0.0.1:18790/health`) [src: docs/concepts.md, docs/architecture.md#WebUI-and-Gateway].
- Flow: Channel → `MessageBus` (`InboundMessage`, bus/events.py+queue.py) → `AgentLoop` (channel-facing: session key, workspace scope, context build, outbound) → `AgentRunner` (model-facing: provider calls, streaming, tool exec, iteration limits) → Provider/Tools → `OutboundMessage` → origin channel [src: docs/architecture.md#Core-Flow; nanobot/agent/loop.py ~2.4k lines, runner.py].
- Concurrency: inbound turns gated by `NANOBOT_MAX_CONCURRENT_REQUESTS` semaphore — **default unlimited since #5572** (unset/≤0 = unlimited) [src: nanobot/agent/loop.py:433-437]. Within a step, tools declare `concurrency_safe` / exclusive; safe tools may batch [src: nanobot/agent/tools/base.py:195-201, runner.py:1678].
- Turn pipeline per message: `restore → compact → command → build → run → save → respond` stages; per-session `asyncio.Lock` serializes turns; mid-turn messages for a busy session go to a per-session pending queue (maxsize 20) for injection; runner guards: 2 empty retries, 3 length recoveries, ≤3 injections/turn over ≤5 cycles [src: loop.py:1239-1360,1683-1691, runner.py:78-81]. Defaults: `max_tool_iterations = 200`, `context_window_tokens = 200,000`, `max_tokens = 8192`, `temperature = 0.1`, default model `anthropic/claude-opus-4-5` [src: config/schema.py:116-158].
- **Sustained goals** (v0.3): `/goal` stores a goal blob in session metadata (`goal_state`, legacy `thread_goal`; objective ≤4000 chars, `status` field); while active, a `max_iterations` stop queues an **invisible internal continuation turn** (sender `system:continuation`, not persisted as user input, synthetic stop message stripped from history) up to `_MAX_GOAL_CONTINUATION_ROUNDS = 12`; the continuation prompt instructs the model to call `update_goal` with `action='complete'` when truly finished; a new/replaced goal resets the round budget; goal lines are injected into the Runtime Context block [src: nanobot/session/goal_state.py:15-21,79-86, nanobot/session/turn_continuation.py:24-33,244-261].
- MCP lifecycle is caller-owned by design: composition roots create `MCPProvider`, share its `ToolRegistry` with `AgentLoop.from_config()`, `connect()`/`aclose()` outside the loop [src: docs/architecture.md#Agent-Loop-vs-Agent-Runner].

### 2. Composition model: flat discovery, no kernel (D2)
- Tools: built-ins discovered by **pkgutil scan** (`ToolLoader.discover()` over `nanobot/agent/tools/`); third-party tools via `[project.entry-points."nanobot.tools"]` [src: pyproject.toml:112-115, docs/architecture.md#Tools].
- Channels: "discovered by scanning self-contained packages under `nanobot/channels/`"; a channel exports a `ChannelPlugin` descriptor; channel packages may carry their own `webui/` assets ("self-contained channels") [src: docs/architecture.md#Channels, pyproject.toml:133].
- Providers: central `ProviderSpec` registry (providers/registry.py) + config schema field; most hosted providers = OpenAI-compatible impl; specialized: Anthropic, Azure OpenAI, Bedrock, OpenAI Codex, GitHub Copilot [src: docs/architecture.md#Providers].
- "Agent Plugins" = v1 packages under `<workspace>/plugins/` enabled from the WebUI Apps page — the installable-capability boundary (bundle MCP servers, skills, tools); "CLI Apps" catalog installs executables and writes a skills-only Agent Plugin [src: docs/architecture.md#Extension-Points, docs/concepts.md#Apps-and-Agent-Plugins].
- No profiles/bundles/patch layering, no service-context composition, no runtime plugin lifecycle (no HMR/unload semantics) — extension = add a package to a scanned directory or edit config.json (live reload via `watchfiles` dep; see §12).

### 3. Channels (D10)
- 17 packages [src: nanobot/channels/ listing]: dingtalk, discord, email, feishu, matrix, mattermost, mochat, msteams, napcat (QQ), qq, signal, slack, telegram, websocket (serves the packaged WebUI on `127.0.0.1:8765`), wecom, weixin (WeChat), whatsapp [measured].
- Each channel maps inbound messages to a session key; `agents.defaults.unifiedSession` deliberately shares ONE session across channels for single-user multi-device use [src: docs/concepts.md#Channels-and-Sessions].
- Access control: per-channel `allowFrom`, pairing (nanobot/pairing/, 338 LOC), WebSocket tokens [src: docs/concepts.md#security, docs/architecture.md#Security-Boundaries].

### 4. Sessions & context (D15/D6)
- Sessions = per-workspace JSONL (`<config-dir>/sessions/<workspace-id>/<url-safe channel:chat>.jsonl`), atomic writes (.tmp+replace), `runtime_checkpoint` sidecar for durable turn recovery ("cancel materializes partial output"; gateway shutdown preserves checkpoints for "Continue"); LRU session cache (128) [src: session/manager.py:42,655-1143, loop.py:1364-1461].
- **Compaction is a soft cursor, not a rewrite**: `Session.last_consolidated` offsets into messages; replay skips `messages[:cursor]` newest-first within a token budget — the JSONL raw trail is never rewritten (auditable); Consolidator summaries append to history.jsonl and inject as `[Archived Context Summary]`; ≤5 rounds targeting `consolidation_ratio` (0.5) of `context_window − max_tokens − 1024`; the cursor advances even on LLM failure, leaving a `[RAW]` breadcrumb [src: session/manager.py:292-317, agent/memory.py:959-1205, loop.py:920-931].
- Context build (`ContextBuilder`): identity template + bootstrap files (`AGENTS.md` from project root; `SOUL.md`/`USER.md` from agent workspace) + tool contract + project section + `# Memory` (MEMORY.md) + `# Active Skills` + recent history = last 50 entries / 8,000-token cap from history.jsonl since `.dream_cursor` + channel metadata as `RuntimeContextBlock`s appended to the user message [src: agent/context.py:81-171,232-259,324-346]. Agent workspace owns identity/memory; project workspace owns instructions/cwd — "no fallback" to agent AGENTS.md when a project is selected [src: docs/architecture.md#Agent-Owned-State].
- Session/fork surfaces are per-surface: TUI commands `/sessions` `/new-chat` `/branch` `/diff`; WebUI uses typed WS envelopes (`new_chat`, `fork_chat`, `set_workspace_scope`…) + Bearer REST (`/api/sessions`, `/api/sessions/{key}/context`) [src: tui/src/command-menu.ts, webui/inbound_commands.py:289-461, tui/src/protocol.ts:674].

### 5. Memory & Dream (D7/D19) — the most distinctive subsystem
- Layers: `session.messages` (live) → `memory/history.jsonl` (append-only, cursor-based compressed archive; `.cursor` write cursor) → durable files `SOUL.md` (voice), `USER.md` (user model), `memory/MEMORY.md` (project facts) [src: docs/memory.md#The-Design].
- **Consolidator** (in-loop): under context pressure, summarizes the oldest safe slice and appends to history.jsonl [src: docs/memory.md#Stage-1; nanobot/agent/loop.py `Consolidator` wiring].
- **Dream** (cron job, default `intervalH: 2`, cron override, optional `modelOverride` to a named model preset): reads new history entries + the three durable files, edits them "surgically in a single pass"; guide file `prompts/dream.md` per workspace; consumption cursor `.dream_cursor` [src: docs/memory.md#Stage-2,#Configuration].
- **GitStore: Dream's edits are recorded as git commits** (dulwich dep) — `/dream-log [<sha>]`, `/dream-restore [<sha>]` audit + restore memory state; "turns memory from a silent mutation into an auditable process" [src: docs/memory.md#Versioned-Memory,#Commands].

### 6. Tools, MCP & skills (D3/D4)
- Built-ins (pkgutil-scanned classes): `read_file`/`write_file`/`edit_file`/`list_dir`/`apply_patch`, `find_files`/`grep`, `exec` (60s default timeout, 600s cap, allowlist/deny-pattern filters) + `exec_session`/`list_exec_sessions` (persistent shells), `run_cli_app` (TUI apps), `web_search` (12 backends: bocha, brave, duckduckgo, exa, jina, kagi, keenable, olostep, searxng, serper, tavily, volcengine) + `web_fetch`, `generate_image`, `cron`, `message` (channel send), `spawn`, `create_goal`/`update_goal`, session-query tools `list_sessions`/`send_session_message`/`read_session`/`search_sessions` [src: nanobot/agent/tools/*.py, web.py].
- Tool ABC carries `read_only`/`exclusive` flags alongside `concurrency_safe`; schemas are a model-facing contract: "Keep user-visible tool names, schemas, and error messages stable unless a change is intentional" — same instinct as DSH's KV-cache discipline [src: tools/base.py:144-227, docs/architecture.md#Tools].
- Safety knobs: `tools.restrictToWorkspace` (schema default `False`; workspace scopes resolve to `restricted`/`full` access modes and gate file/shell/message/image tools — shell prompts the model to work within policy rather than hard-failing) and `maxToolResultChars` (default **16,000**, truncation in-loop and in context governance) [src: nanobot/config/schema.py:132,410, security/workspace_access.py:211-212, agent/tools/shell.py:90, agent/context_governance.py:126-136].
- MCP: `tools.mcpServers` config — **stdio** (`command`), **sse** (url ends `/sse`), **streamableHttp** (default) via the official `mcp` SDK ≥1.26; tools named `mcp_{server}_{tool}` (sanitized + hash-truncated), and **Resources/Prompts are wrapped as tools too** (`mcp_<server>_resource_<name>`, `mcp_<server>_prompt_<name>`) where DSH defers them; `MCPProvider.reload()` hot-reloads added/changed/removed servers; session-termination auto-reconnect then call retry [src: tools/mcp.py:176-199,595-620,1000-1136,1346-1663, pyproject.toml:44].
- Runtime self-inspection is also **model-mutable**: the `self` tool's runtime-control protocol exposes setters (e.g. `set_max_tool_result_chars`) so the model can adjust its own runtime knobs live [src: nanobot/agent/tools/runtime_control.py:107,204-205, tools/self.py:578-579].
- Skills (D4): `SKILL.md` + YAML frontmatter (`name`, `description`, nanobot metadata incl. `always` and **openclaw-compat metadata**); sources = workspace `skills/`, bundled `nanobot/skills/`, Agent Plugins; `always`-on skills inject into the system prompt, explicit invocation via `@`-mention delivered as a runtime-context block; 11 bundled skills (clawhub, cron, github, image-generation, memory, my, skill-creator, summarize, tmux, update-setup, weather) [src: agent/skills.py:15,51-92,148-193, nanobot/skills/].

### 7. Subagents (D8)
- One tool, `spawn(task, label?, temperature?, wait?)`: default background (`SubagentManager.spawn`); `wait: true` = inline consultation (`run_inline`) whose result returns into the current turn [src: nanobot/agent/tools/spawn.py:24-46,96].
- Spawn carries origin channel/chat/session-key + `current_workspace_scope()` — subagents inherit workspace scope and report back to the origin channel [src: spawn.py:90-107].
- Execution: asyncio tasks in-process under a shared runtime; manager serializes capacity admission [src: spawn.py:77-79]. Concurrency default `agents.defaults.max_concurrent_subagents = 4` (`ge=1`), Semaphore-admitted (`_run_slots`) [src: nanobot/config/schema.py:131, nanobot/agent/subagent.py:146-151]; the documented "one subagent at a time" predates v0.3.
- Isolation: subagents run `AgentRunner` with an **isolated `ToolRegistry` (`scope="subagent"`) minus message/cron/spawn — no recursive spawning and no channel delivery**; status phases `queued→initializing→awaiting_tools→tools_completed→final_response→done|error` are in-memory only [src: subagent.py:198-227,356-452].
- Result delivery: background results are **published back through the bus as an inbound message** (`sender_id: "subagent"`, `injected_event` metadata) into the parent's pending queue, marked hidden-history; loop waits ≤300s for running subagents at shutdown [src: loop.py:1040-1050,1069-1101].

### 8. Scheduling / background work (D9)
- Gateway starts a **workspace-scoped cron service** (croniter; store `<workspace>/cron/jobs.json`, corrupt-backup protection): schedules `at | every | cron(+tz)`; jobs tick into **scheduled inbound turns** in their origin chat/session, and automation turns for a busy session are **deferred** (`_deferred_automation_turns`) and republished after completion [src: cron/types.py:27-185, cron/service.py, loop.py:1281-1296,1473-1499].
- **Heartbeat** = protected system cron job (default `interval_s = 1800`): reads `<workspace>/HEARTBEAT.md`, acts only if `## Active Tasks` has non-comment lines, in a dedicated `heartbeat` session keeping last 8 messages; delivery is gated by a **lightweight evaluator LLM** (`utils/evaluator.py`, `/evaluator-prompt` override) that suppresses "nothing changed" results [src: cli/gateway_runtime.py:626-666,844-857, utils/evaluator.py, templates/HEARTBEAT.md].
- **Local triggers**: `/trigger <name>` binds a session; `nanobot trigger <id> "<msg>"` injects from external scripts; delivery is **file-based with inbox/processing/failed dirs** — claim on enqueue, recovery of in-flight deliveries on restart ⇒ **at-least-once**; busy-session deferral honored [src: triggers/local_store.py:41-260, loop.py:423-432].

### 9. Models / providers (D5)
- Registry-driven selection: explicit provider → registry keywords → API-key prefix/base-URL hints → local fallback when `apiBase` set → gateway fallback for multi-family routers [src: docs/architecture.md#Providers]. Provider modules: OpenAI-compat (chat-completions **and Responses API**), Anthropic, Azure OpenAI, Bedrock (Converse), GitHub Copilot, OpenAI Codex (+OAuth), xAI Grok (+OAuth), transcription, image generation, fallback, registry, factory [src: nanobot/providers/ listing].
- `FallbackProvider` tries ordered fallback presets but **skips fallback once content has streamed** (except timeout recovery into a new segment) — strict no-cross-source answers, same policy family as OpenClaw's selection-source rule [src: providers/fallback_provider.py:98-118,414-443].
- Named `model_presets`; **per-session model switching from the WebUI composer** (v0.3.0 "Agency" feature); Dream can pin a preset via `modelOverride`; streaming requests `include_usage` [src: docs/memory.md#Configuration, README release notes, openai_compat_provider.py:2073-2096].

### 10. API / SDK / WebUI / TUI (D16/D10)
- **OpenAI-compatible API** (optional `api` extra, aiohttp, default `127.0.0.1:8900`): `POST /v1/chat/completions` (JSON + multipart; SSE `stream` ending `data: [DONE]`), `GET /v1/models`, `/health` (unauthenticated); optional Bearer-key auth (`hmac.compare_digest`); wildcard-host-without-key config is validated against; requests run in a synthetic `api` channel (session `api:{id}`, no auto-delivery to chat channels) [src: nanobot/api/server.py:3,47,294,448-466,479-519, schema.py:342-358].
- **Python SDK** (nanobot/sdk/: clients, runtime, streaming, types) for embedding the loop in other programs [src: nanobot/sdk/ listing].
- **WebUI**: React 18 + TypeScript + Vite + Tailwind/Radix (bun build) → production build written to `nanobot/web/dist/` and **bundled into the wheel**; served by the WebSocket channel (default `127.0.0.1:8765`, token handshake mints `webui`-audience tokens) with a Bearer REST surface (`/api/sessions`, `/file-preview`, `/automations`); server half 16.8k LOC [src: webui/package.json, docs/architecture.md#WebUI-and-Gateway, channels/websocket/runtime.py:163-193, pyproject.toml:134-141].
- **TUI**: a separate **TypeScript/OpenTUI app** under `tui/` (not the Python prompt-toolkit layer, which powers the onboard wizard) with its own command set (`/sessions`, `/new-chat`, `/branch`, `/diff`) and a hosted-client mode inside the "Herdr" terminal workspace [src: tui/README.md, tui/src/command-menu.ts, docs/cli-reference.md:99-101].

### 11. Config & instances (D15/D17)
- One `config.json` per instance (`~/.nanobot/config.json`), camelCase/snake_case duality, written back camelCase; `nanobot onboard` creates it; runtime paths derive from config location [src: docs/concepts.md#Config-Format, docs/multiple-instances.md].
- **Live config reload**: `watchfiles` dep; v0.3.0 notes "apply configuration changes live across a more reliable provider, channel, and tool runtime" [src: pyproject.toml:53, README].
- Multiple instances = N configs + N workspaces + N processes (`--config`/`--workspace`, per-instance port); no in-process multi-profile concept [src: docs/multiple-instances.md].
- Deployment: Dockerfile + docker-compose (and bwrap variant), render.yaml (Render.com), systemd user service guide with linger note [src: repo root; docs/deployment.md existence].

### 12. Security posture (D13/D14) — deliberately thin
- Present: channel `allowFrom` (exact opaque-token match or `"*"`; **omitted ⇒ pairing-only mode**), pairing codes (`ABCD-EFGH` format, TTL'd, `~/.nanobot/pairing.json`), WebSocket static + short-lived issued tokens (`nbwt_`, default TTL 300s) + trusted-proxy auth, API Bearer key, loopback-only default binds, `tools.restrictToWorkspace` + shell allowlist/deny patterns + private-URL guard, MCP URL validation/SSRF probes, internal message-metadata keys refused from untrusted clients, secrets masked (only) in the onboard TUI [src: channels/base.py:242-301, pairing/store.py:28-48, channels/websocket/runtime.py:163-193, tools/shell.py:805-905, tools/mcp.py:239-307, bus/events.py:15-18, cli/onboard.py:339-344].
- Absent: **no tool-call approval/confirmation gate**, no in-process OS sandbox (bwrap is a deployment-time compose overlay; the agent merely *detects* it), no credential store/encryption (provider keys sit in plaintext config.json), no read-before-write freshness guards, no permission presets. Trust model = "keep allowFrom narrow" + human reviews remote instructions [src: surveyed tree; docs/agent-social-network.md#Security-Model warnings].

### 13. Reverse absence: what DSH has that nanobot does not
No config-layered composition (profiles/bundles/patch rows), no swappable-loop/seam grammar, no append-only typed event log ("log-is-the-trace" — sessions are JSONL transcripts + history.jsonl, not a SessionEventMap), no guarded tool pipeline (no pre/post policy hooks, no frozen arguments, no deny-monotonic guards), no approval seam, no OS confinement runners in core, no plan mode, no workflow engine or Ralph-style fresh-agent loops, no headless stdout contract, no in-session dynamic plugin authoring, no oversized-output spill, no runtime invariant checks, no OTel telemetry seam (Langfuse only), no LSP seam. Subagents = single-shot spawn + bus-injected result with in-memory status and `cancel_by_session` — no durable/continuable children, no child→parent report *tool*, no message-into-live-child; chat fork exists only as surface commands (TUI `/branch`, WebUI `fork_chat` envelope), not a sessions API [src: nanobot/agent/subagent.py:156-165,280-282,496-512,564]. A sustained-goal analogue *does* exist (see §1) — convergent with DSH's goal model rather than absent. [src: absence across surveyed tree; DSH baseline §5]

### 14. The minimalism reveal (ticket's special angle)
1. **"Ultra-lightweight" is a claim about the core path, not the system** — ≈99k Python LOC excl. tests (≈129k incl. per-channel tests), but the infrastructure floor is tiny: bus 645, cron 1.2k, gateway 0.9k, api 0.5k LOC and the channel-facing loop (loop.py) ≈2.4k lines; breadth (17 channels ≈52k, ~10 provider backends, an embedded React webui) is packaged as *scanned directories*, so the core never grows when breadth does. DSH achieves the same via seams; nanobot shows a cheaper convention (directory + entry-point scan) suffices at personal-agent scale.
2. **Chat channels, memory, cron, persona — the four DSH-absent dimensions — are nanobot's center of gravity and are all files + one bus.** MEMORY.md/SOUL.md/HEARTBEAT.md are user-editable files; the "memory system" is a summarizer + a cron job + git. Nothing here needs a kernel; a DSH plugin family (channel provider + workspace files + existing `schedule` seam) is not absurd on its face.
3. **MCP outside the loop is a load-bearing simplification**: by making MCP lifecycle caller-owned, the loop stays provider-agnostic and MCP never appears in loop code — contrast DSH's opt-in `dsh-mcp-client` bundle row doing the same inside the composition system.
4. **Auditability migrated from the log to the artifacts**: DSH audits turns (session log); nanobot audits *memory mutations* (GitStore + `/dream-log`/`/dream-restore`), never rewrites the raw session trail (soft-cursor compaction), and exposes context inspection (`/context` docs; REST `/api/sessions/{key}/context`). DSH has neither memory-mutation auditing nor a user-facing "show the model's exact context" surface.
5. **Concurrency defaults are env-var pragmatism** (`NANOBOT_MAX_CONCURRENT_REQUESTS`), not per-owner caps or admission waterfalls — simplest possible backpressure.
