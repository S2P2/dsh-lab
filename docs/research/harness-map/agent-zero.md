# Agent Zero: computer-as-environment agent framework (vs DSH baseline)

**Baseline for:** Agent Harness Capability Map (profile #7 of 18)

**Verdict.** Agent Zero is a *computer-first* agent framework: one Dockerized Kali Linux container (XFCE desktop streamed via Xpra, Patchright/Playwright browser, LibreOffice, SearXNG, SSH, two Python runtimes) that the agent operates as a real GUI computer while the human shares the same screen — the exact inverse of DSH, where the host is trusted, execution is confined by OS-level sandboxes, and browser/desktop control is deliberately absent (D12). Its extension philosophy is "filesystem as plugin system": capability = a directory with conventions (`plugin.yaml`, `tools/*.py`, `prompts/*.md`, `extensions/python|webui/<point>/`), extension points are folder paths (plus an `@extensible` decorator that turns any function into implicit start/end hooks with mutable args/result/exception), and layered roots (`usr/`, project, agent profile, bundled `_plugin`) resolve first-occurrence-wins — shadowing by file placement where DSH uses typed service registries and patch rows. Nearly every product feature — memory, browser, desktop, office cowork, goal strip, tool policy, even prompt-injection checking — is a bundled `_`-prefixed plugin over a small framework core (agent loop in `agent.py`, LiteLLM model layer, Flask+Alpine.js+Socket.IO WebUI), a looser but recognizable cousin of DSH's everything-is-a-plugin stance. Headline divergences: persistent vector memory + per-project isolation (D7: DSH absent by design), real browser/desktop control (D12: DSH absent), and cron-style scheduling (D9: DSH deliberately minimal) — versus DSH's unmatched structural assets Agent Zero lacks: event-sourced durable log with replay/fork, typed capability seams, guarded tool pipeline with one-shot approvals, OS confinement runners, and a permission model at all (Agent Zero's agent effectively owns a root container; safety doctrine is "keep it in Docker").

## Architecture profile

### 1. Positioning & runtime shape (D1)
- **One Dockerized computer per agent instance.** Image `agent0ai/agent-zero` builds on a Kali base (`docker/base/Dockerfile:2` `FROM kalilinux/kali-rolling`; run/AGENTS pins desktop packages to `kali-last-snapshot` with pinned Xpra + LibreOffice versions, docker/run/AGENTS.md:22). Ports: SSH 22, HTTP 80, tunnel range 9000-9009 (`docker/run/Dockerfile:31`); entrypoint `/exe/initialize.sh` → supervisord (:33,36); persistent state volume `/a0/usr` (README:92).
- **Two-runtime model:** Python 3.12 framework venv `/opt/venv-a0` (WebUI, APIs, scheduler, plugin hooks) vs Python 3.13 agent-execution venv `/opt/venv` (agent terminal tasks, user code) — docker/AGENTS.md:16. Framework and executed code isolated by venv, not by sandbox.
- **Stack:** Flask + Alpine.js + Socket.IO WebUI; LiteLLM model layer wrapped as a LangChain `SimpleChatModel` (`models.py:367` `LiteLLMChatWrapper`); core loop in `agent.py` (`Agent`, `AgentContext`, `LoopData`), per-helper/tool file-level DOX contracts throughout.
- **Loop:** `monologue()` = open inner loop until a `response` tool returns `break_loop` (root AGENTS.md contract; `helpers/tool.py` `Response(message, break_loop)`). Extension points fire at every stage — `monologue_start`, `message_loop_start`, `before_main_llm_call`, `reasoning_stream_chunk`, `response_stream_chunk`, `message_loop_result` (with `skip_default_processing` short-circuit), `message_loop_end`, `monologue_end` — agent.py:391-560. Tool requests are parsed **mid-stream** from partial text (`extract_tools.extract_tool_request` in `stream_callback`, agent.py:458-467). Tool declarations live in prompt markdown with fenced JSON examples; lenient `DirtyJSON` parsing repairs malformed calls (`helpers/dirty_json.py`, root AGENTS.md prompt contract).
- **Prompt assembly is extension-driven:** `get_system_prompt()` returns only what extensions appended (agent.py:682-688); `prepare_prompt` joins system + protocol block (`agent.context.protocol.md` over persistent+temporary dicts) + history + extras (agent.py:563-622). Even exception handling is delegated to extensions (`handle_exception` re-raises unless intercepted — agent.py:642-645; `_error_retry` plugin owns retries).
- **Agents and contexts:** agents numbered `A1, A2…` with `_superior`/`_subordinate` links (agent.py:361-381); `AgentContext` registry with a recursive shared `get_data/set_data` tree (agent.py:176-190); `handle_intervention()` gives the human pause/steer at every loop stage; three model roles per agent — chat, utility (small helper model), embedding (agent.py:816-824).

### 2. Computer-as-environment: Docker desktop, browser, code execution (D12/D13/D11)
- **Capability — full Linux desktop:** XFCE session in the container, streamed into the WebUI right-side Canvas via Xpra HTML5; the agent uses a Linux-Desktop skill to "observe the visible state, act through the app" (screenshot-observe + GUI-act loop), and the human shares the same mouse/keyboard (docs/guides/desktop.md:17-29,100-111). **Mechanism:** token-addressed `VirtualDesktopEndpoint` sessions proxied through the WebUI; `xrandr` mode adds/resize, window find/close by class (helpers/virtual_desktop.py.dox.md:14-44).
- **Capability — browser with DOM annotation:** agent reads pages as element refs `[link 1]`, `[button 2]`, `[input text 3]` and acts on them; advanced actions incl. `evaluate`, `key_chord`, `mouse`, `clipboard`, `set_viewport`, `multi`; screenshots persist per step into chat history (docs/guides/browser.md:48-91). **Annotate mode** is the human-directed inverse: user clicks an element and pins a comment/change/lift instruction into the chat (browser.md:93-103). **Mechanism:** bundled `_browser` plugin = Playwright/Patchright inside the container (`patchright install chromium`, browser.md:237; plugins/AGENTS.md:73); optional separate **Browser LLM preset** (helper model) for browser work (browser.md:113).
- **Bring Your Own Browser:** drive the user's real Chrome/Edge/Brave/Opera/Vivaldi on the host via CDP remote-debugging endpoints relayed through the A0 CLI connector; page-content access policy tiers (local-models-only / warn / allow) (browser.md:144-209).
- **Code execution:** `_code_execution` plugin — terminal, Python, and Node.js tools over `shell_local.py`/`shell_ssh.py`/`tty_session.py` helpers (plugins/_code_execution tree; plugins/AGENTS.md:80), running in the Py3.13 execution venv.
- **Security posture = the container is the boundary.** No USER downgrade in either Dockerfile (inference: agent session runs as container root; not runtime-verified). README Safety Model: "keep it running inside Docker… do not mount your entire home directory" (README:304-312). In-container mitigations: `_infection_check` (prompt-injection analysis before tool execution), `_tool_access` (always-on project/profile tool-policy gate) — plugins/AGENTS.md:88,106. No per-call approval waterfall, no OS confinement runners.

### 3. Extension architecture: plugins, extensions, dynamic tools (D2/D3/D4)
- **Extensions = folder paths.** `call_extensions("<point>")` loads every `Extension` subclass from `extensions/python/<point>/` folders across layered roots resolved by `subagents.get_paths(agent, …)` (agent profile → project → user `usr/` → bundled → enabled plugins) — helpers/extension.py:326-351. First occurrence by filename wins (override by placement; extension.py:341-349), classes sorted alphabetically (bundled points use `_90`-style filename prefixes to control order). Watchdog hot-reload clears caches on file change (extension.py:372-406). WebUI extensions are `extensions/webui/<point>/*.html|js` files injected into the UI by manifest (extension.py:287-323) — dual-face pattern.
- **`@extensible` decorator = implicit AOP.** Wraps any function to emit `_functions/<module>/<qualname>/start|end` points with mutable `args/kwargs/result/exception` — extensions can rewrite inputs, short-circuit, replace results, or force-raise (extension.py:57-214). Core methods (`Agent.__init__`, `monologue`, `prepare_prompt`, `get_system_prompt`…) are themselves decorated.
- **Plugins = convention directories.** `plugin.yaml` manifest + optional `hooks.py` (lifecycle, framework runtime), `execute.py` (manual maintenance), `tools/`, `prompts/`, `skills/`, `extensions/`, `webui/config.html` (settings UI), `default_config.yaml`, `conf/model_providers.yaml` (provider entries merge into base catalog), API handlers at `GET /plugins/<name>/<path>` + `POST /api/plugins/<name>/<handler>`, banners/discovery cards — plugins/AGENTS.md:11-43. ~40 bundled `_`-prefixed plugins ship the product surface (memory, browser, desktop, office, editor, goal, time_travel, tool_access, infection_check, telegram/whatsapp/email, oauth, model_config, a0_connector, a0_acp…). Bundled names must start `_` to avoid colliding with community plugins (:20).
- **Scoping:** plugin settings resolve project/profile → project → user/profile → user → default (:27); enable/disable toggles are marker files with independent global vs project vs agent-profile state; `always_enabled` plugins refuse disabling (:30; helpers/plugins.py.dox.md:52-57).
- **Plugin Hub:** community index at `agent0ai/a0-plugins` (index.yaml per plugin; docs/developer/plugins.md:53-56); `_plugin_installer` installs from ZIP/Git/Index; `_plugin_validator` checks manifest/structure/security conventions; `_plugin_scan` is an **LLM-guided security scanner** for third-party plugins (plugins/AGENTS.md:98-100).
- **Tools:** `Tool` subclass, `execute()` → `Response(message, break_loop)`, `before/after_execution` hook points, streaming `set_progress`; tools discovered from root `tools/`, plugin `tools/`, and profile-local `agents/<profile>/tools/` (tools/AGENTS.md:16-21). Files not ending `.py` don't load (`helpers/modules.py:38`) — the `._py` files in `tools/` (browser._py, browser_open._py, knowledge_tool._py) are **disabled-by-rename** tool variants.
- **Dynamic tools/extensions by the agent itself:** everything the loop consumes is an editable file in layered roots with watchdog reload, and the shipped skill set includes `a0-create-plugin`, `a0-create-agent`, `a0-manage-plugin`, `a0-review-plugin`, `build-skill` (skills/ dir) — the intended workflow is the agent authoring its own tools/plugins/skills into `usr/` at runtime; root AGENTS.md contracts even cover copying live agent-edited plugin changes back into tracked source. No confirmation gate on self-authored code beyond it living in `usr/`.

### 4. Memory & knowledge (D7)
- **Capability — persistent vector memory per scope:** remembers facts, solutions, preferences across chats; scoped by subdirectory/context = profile/project (plugins/_memory/AGENTS.md:9,17). Areas: `main`, `fragments`, `solutions`, `skills` (docs/guides/memory.md:34); memory dashboard UI with similarity threshold/limit, edit/delete, curation doctrine ("long-term AI memory is not a solved problem… needs human gardening", memory.md:5-10,62-135).
- **Mechanism:** `_memory` plugin — FAISS store loading + embedding metadata (helpers/memory.py), knowledge import + consolidation (`memory_consolidation.py`), tools `memory_save/load/delete/forget` + behavior adjustment (plugins/_memory/AGENTS.md:9-13). **Auto-recall:** each prepared query is embedded once and the vector reused for memory + solution filters; results are delayed into the next prompt, consumed once, and never persisted as live objects (:21-22). Manual `memory_load` takes `threshold`/`limit` (:20). Bundled `knowledge/` (main + solutions) ships agent self-knowledge; projects add `.a0proj/knowledge/`.

### 5. Projects, agent profiles, model presets (D15/D2/D5)
- **Projects** isolate workdir + instructions + memory + knowledge + secrets + MCP servers + subagent availability: a project dir with `.a0proj/` meta (`instructions/`, `knowledge/`, `skills/`, `mcp_servers.json`, header, `agents.json` availability overrides) — helpers/projects.py.dox.md:63,69-77. Create-from-git-clone with http token (:26). Activation is per chat context; project AGENTS.md chain walked root-to-target with `AGENTS.override.md` precedence (:74-75). README:226,36.
- **Agent profiles** = persona folders `agents/<name>/` (`agent.yaml` title/description/context + optional `prompts/` + `tools/` + `extensions/`), shipped: `default`, `agent0`, `developer`, `hacker`, `researcher`, `tiny-local`; user profiles in `usr/agents/` (agents/AGENTS.md:10-45). Merging is presence-aware: a missing key inherits from base, an explicitly-empty value clears it (helpers/subagents.py.dox.md:17-18,48-51). Profiles serve both as chat personas and as subordinate templates (per-project enablement; call_subordinate validates the name).
- **Model layer:** LiteLLM unified provider catalog (`conf/model_providers.yaml`, plugins may merge more); per-service API keys, rate limiter, transient-error retry, thinking-tag stream processing (models.py:60-367). OAuth plan logins (`_oauth` plugin; OpenAI Codex device-code flow first, README:183-190). **Model presets** = named model-setup shortcuts switchable per chat (README:232; `_model_config` plugin, plugins/AGENTS.md:92); per-agent chat/utility/embedding roles (§1).

### 6. Scheduled work & background jobs (D9)
- **Capability — agent-managed scheduled tasks:** the `scheduler` tool exposes create/update/list/run/wait/delete over three task kinds (tools/scheduler.py.dox.md:6,16-30): `ScheduledTask` (recurrence incl. cron via `TaskSchedule.to_crontab()`, timezone-aware — pytz + localization aliases), `AdHocTask` (one-shot with token), `PlannedTask` (a todo/in-progress/done plan of datetimes — plan-driven recurrence). Tasks carry their own `system_prompt`, `prompt`, attachments, `context_id`, and project — each run spawns an agent turn in a (optionally dedicated) chat context (helpers/task_scheduler.py.dox.md:26-50).
- **Mechanism:** `SchedulerTaskList` persisted; `TaskScheduler` singleton runs in the framework runtime (venv-a0, docker/AGENTS.md:16) with `job_loop.py`; cancel by uuid or context; v0.80 chat migration handles old tasks (helpers/persist_chat.py.dox.md:22). Use case framed as "recurring checks and monitoring with project-scoped context and credentials" (README:264).
- **Parallel/background tools:** `parallel.py` tool runs tools concurrently; long-running tools call `handle_intervention` for pause; no generic user-visible background-job registry (DSH's `job_*` has no direct counterpart; nearest is the scheduler task list UI).

### 7. Multi-agent cooperation (D8)
- **Subordinates (in-process hierarchy):** `call_subordinate` (Delegation tool) — every child is a full `Agent(parent.number + 1)` (A1→A2…) in its **own persisted child-chat context**; `reset=true` fresh, `reset=false` continues the caller's default child or the exact `context_id` child; child IDs validated against persisted parent/depth; profile changes on an existing child raise `RepairableException`; children inherit caller's project + selected chat model; parallel children have stable IDs, non-concurrent continuation enforced (tools/call_subordinate.py.dox.md:30-39). Projects can restrict which profiles are spawnable (§5).
- **Inter-instance RPC:** `rfc.py` = remote function call dispatch module.function over HTTP with password + crypto-verified payloads (`call_rfc`/`handle_rfc`, helpers/rfc.py.dox.md:17-32) — Agent Zero instance ↔ instance (incl. A0 CLI host bridge) cooperation substrate.
- **A2A interop:** FastA2A server exposes Agent Zero as a standard A2A agent — agent card with streaming capability forced true, worker run/cancel tasks, artifacts (helpers/fasta2a_server.py.dox.md:14-34); `a2a_chat` tool messages external A2A agents with a per-URL conversation cache (tools/a2a_chat.py.dox.md); setup guide docs/guides/a2a-setup.md.
- **ACP:** `_a0_acp` plugin = "Agent Client Protocol — connect ACP-capable editors through the local A0 CLI connector" (plugins/_a0_acp/plugin.yaml) — the same editor-integration protocol DSH's `dsh-acp` serves.
- **Adjacent:** `_orchestrator` plugin orchestrates *external* terminal coding agents (plugins/AGENTS.md:96); `_goal` plugin is a light goal strip + `/goal` + goal tools (:87) — far thinner than DSH's durable goal model.

### 8. Persistence, context management, channels (D15/D6/D10)
- **Persistence = JSON snapshots, not event sourcing:** each chat context serializes (context + agents + log) to `chat.json` via temp-file + fsync atomic replace; message artifacts stored separately; `SAVED_CHAT_CONTEXT_DATA_KEY` marks disk-backed chats; v0.80 migration exists (helpers/persist_chat.py.dox.md:16-50). No append-only event log, no replay/fork/derive — **fork/branching is a UI feature instead**: `_chat_branching` branches from any message (plugins/AGENTS.md:74), vs DSH fork-at-turn-boundary from the log.
- **Time Travel:** `/a0/usr` workspace snapshot history with diff/travel/revert (shadow history under `usr/.time_travel/`, skipped by self-update backups) — `_time_travel` plugin + docker/run/AGENTS.md:26 + README:246-252. Explicitly "not a replacement for Git".
- **Context management:** `_chat_compaction` (full-chat summary message), `_context_window` (token accounting, composer indicator), `_context_doctor` (tool-call JSON repair + compact persistence pre-dispatch) — plugins/AGENTS.md:75,78-79; recent commit "Refresh context usage during generation" (pinned HEAD).
- **Channels:** WebUI (Flask/Alpine/Socket.IO, Canvas with desktop/browser/editor/office surfaces); A0 CLI connector (terminal bridge to a running instance, incl. host browser + host file access — README:192-222); `_telegram_integration` (per-user chat sessions), `_whatsapp_integration` (Baileys), `_email_integration` (IMAP/Exchange poll + SMTP reply) (plugins/AGENTS.md:103,107,85); outbound tunnels (cloudflare/serveo/microsoft/tailscale helpers, `run_tunnel_api.sh`, ports 9000-9009).
- **MCP both ways:** client — global + per-project `mcpServers` JSON, `MCPServerLocal/Remote`, `MCPTool` wrapped into the Tool contract (helpers/mcp_handler.py.dox.md:6,14-45; per-project config `.a0proj/mcp_servers.json`, projects.py.dox.md:69); server — Agent Zero chats exposed as MCP tools via a dynamic MCP proxy (helpers/mcp_server.py.dox.md:6).

### 9. What each side has that the other lacks (absence is data)
- **Agent Zero has, DSH lacks:** persistent FAISS memory + curation UI (D7); real GUI desktop + screen-act loop and Playwright browser with DOM refs (D12); cron/timezone/plan scheduler spawning agent runs (D9); chat-platform integrations (D10); live-cowork document/office surfaces (D18); plugin marketplace with LLM security scanner (D2); per-project isolation bundles; A2A agent-to-agent interop; utility-model role.
- **DSH has, Agent Zero lacks:** append-only event-sourced session log with replay/fork/search/invariants ("model-visible means logged" — AZ snapshot-serializes instead); typed capability seams with generated ownership graphs vs folder conventions; guarded tool pipeline (pre/around/post policy, frozen args, one-shot approval waterfall, permission presets) vs no per-call approvals; OS-level confinement runners (bwrap/Landlock/Seatbelt/ACL) vs whole-agent-Docker only; KV-cache stability discipline (AZ reassembles prompt sections per turn); Code Mode / workflow-script orchestration languages; headless one-shot CLI with exit-code contract; embedding SDK; OTel telemetry seam; durable goal model. (MCP cuts both ways: both harnesses ship it config-activated rather than on by default — DSH via opt-in `dsh-mcp-client` mounted by no shipped bundle, AZ via `mcpServers` config.)
