# Eigent: open-source Cowork desktop with a CAMEL multi-agent workforce — architecture & capability profile

**Verdict.** Eigent ([eigent-ai/eigent](https://github.com/eigent-ai/eigent)) is the inverse packaging of DSH: not a composable harness but a *productized desktop app* — an Electron+React shell around a local Python agent runtime built on CAMEL-AI, plus a separate cloud backend for accounts, credits, and model proxying. Its center of gravity is the **multi-agent workforce as UX**: a CAMEL `Workforce` subclass decomposes a user task into a visible, *user-editable* subtask tree, assigns subtasks over a TaskChannel to predefined specialist workers (browser/developer/document/multi-modal/MCP/social-media), with pause/resume, retry/replan failure handling, and human-ask escalation. A **single-agent harness mode** (one root agent, depth-1 delegation cap, all toolkits assembled into one) is the low-friction alternative — both paths share memory-recovery helpers. Distinctive capabilities DSH lacks: browser/computer-use tooling with persistent login/cookie state, ~40 built-in consumer-app toolkits, MCP marketplace/search + one-click install, scheduled/webhook/Slack trigger automations, and a credits/proxy subscription runtime. Structurally it is far less orthogonal than DSH: an in-process Action bus and HTTP controllers instead of an event-sourced durable log, a fixed agent loop and fixed worker roster instead of seams/plugins, ask-only human gating instead of a guarded tool pipeline, and no sandbox or permission engine.

## 1. Positioning & layout

Self-describes as "The Open Source Cowork Desktop — Local and Free Alternative to Claude Cowork and Codex" (README), built on CAMEL-AI; sells an enterprise tier (SSO/access control, custom integrations, RL environments — README §Enterprise). Quick-start `npm run dev` mode **connects to Eigent cloud services and requires account registration**; "fully standalone" = Local Deployment (README). Four top-level surfaces:

| Dir | Role |
|---|---|
| `electron/` | Desktop main process: spawns/supervises the local Python backend (`python_process`, default `backendPort: 5001`, `startBackend`/`getBackendPath` — `electron/main/index.ts:93-95,126-172`), PTY terminal (`main/terminal.ts`), embedded webviews (`main/webview.ts`), GitHub-releases-CDN auto-update (`main/update.ts`, `githubReleaseCdnProvider.ts`), subscription OAuth (Codex) + OS credential store (`main/subscriptionAuth/*`), MCP config file utils (`main/utils/mcpConfig.ts`) |
| `src/` | React 18 + Zustand renderer; REST + SSE client (`src/api/http.ts`), stores, task/workforce UI, React Flow editor, AddWorker/ModelSelect/MCP UI |
| `backend/` | Local agent runtime (Python, uv): `app/agent` (CAMEL agents + ~40 toolkits), `app/service/task.py` (Action bus), `app/controller/*` (FastAPI routes), `app/hands` (resource hands), `app/memory`, `app/remote_sub_agent` |
| `server/` | Cloud backend: FastAPI + Celery + alembic + docker-compose; accounts, credits, model proxy (`proxy.eigent.ai`), SSE step sync (`backend/app/utils/server/sync_step.py:17` "Syncs SSE step data to cloud server") |

Client/runtime boundary: renderer ⇄ local backend over loopback REST (`/chat`, `/task/{id}/start`, `/mcp/*`, `/skills/*`, `/files`, `/browser/cdp/*`, `/workspace/*` — `app/controller/*.py`) plus **HTTP + SSE** step streaming via `@microsoft/fetch-event-source` (`src/api/http.ts:319-352`); WebSocket appears only for cloud execution subscription and remote control (`src/hooks/useExecutionSubscription.ts:231`, `src/pages/RemoteControl.tsx:170`). Auth headers per call: `Bearer` token (relative Brain URLs only), `X-User-ID`, `X-Session-ID`, `X-Channel` (`src/api/http.ts:62-84`); base URL via Electron IPC `get-backend-port` or `VITE_BRAIN_ENDPOINT`, dev `localhost:5001` (`src/api/http.ts:91-111`). Cloud-vs-local is a store flag `authStore.modelType: 'cloud'|'local'|'custom'|'codex_subscription'` (`src/store/authStore.ts:34`); cloud calls go through proxy fetchers (`VITE_PROXY_URL`, `src/api/http.ts:357-427`), and response `code:20/21` trigger credits/storage toasts (`src/api/http.ts:193-211`; credits UI `GET /api/v1/subscription`, `GET /api/v1/user/current_credits` — `src/pages/Agents/Models.tsx:1231,1244`). The ~30-value SSE step vocabulary `AgentStep` (`src/types/constants.ts:18-49`) mirrors the backend Action bus one-for-one. Electron main owns process lifetime (§Packaging), serves agent files through a privileged `localfile://` protocol with a path-traversal guard (`electron/main/index.ts:3360-3455`), and pools CDP browsers on ports 9223-9299 with state in `~/.eigent/cdp-browsers.json` (`index.ts:112-419`). Vestigial vocabulary: `ClientType` already names `'cli','browser_extension','whatsapp','telegram','slack','discord','lark'` (`src/client/platform.ts:18-27`) — channel targets absent elsewhere in the read surface. Cloud mode routes model calls through the Eigent proxy, detected by URL markers `"eigent-proxy"`, `"proxy.eigent.ai"` (`app/agent/agent_model.py:146-150`).

**Packaging & deployment.** Desktop app v1.0.2 ships the Python backend as `extraResources` with **prebuilt uv + bun + venvs** (`electron-builder.json:26-48`); `startBackend()` copies the prebuilt venv to `~/.eigent/venvs/backend-{version}` (shebang/symlink fixes — `electron/main/utils/process.ts:176-470`), spawns `<venvPython> -m uvicorn main:api --port <port> --loop asyncio` (or `uv run` with self-repair `uv python install 3.11` + `uv sync`; Aliyun mirror on Asia/Shanghai tz) (`electron/main/init.ts:371-532`), free-port scan from 5001, and health-polls `/health` 1s up to 5 min (`init.ts:601-674`). A separate terminal venv carries pandas/numpy/matplotlib/… for the code toolchain (`process.ts:1096-1105`). Real PTYs via `node-pty` with sensitive-env (`API_KEY|TOKEN|PASSWORD`) stripping (`electron/main/terminal.ts:21-90`). Auto-update: electron-updater over a custom CDN feed `https://cdn.eigent.ai/releases` backed by a GitHub-releases provider (`electron/main/update.ts:77-91`, `githubReleaseCdnProvider.ts:42`).

## 2. Architecture profile

**Agent core.** `agent_model()` (`app/agent/agent_model.py:56-314`) is the one factory: builds a CAMEL `ModelFactory` model (per-agent custom platform/type/key/url override over task defaults), wraps it in `ListenChatAgent` (a CAMEL `ChatAgent` subclass with task-tracking; `app/agent/README.md:76`). Notable model plumbing: subscription runtime rebuilds models mid-flight via `model_reload_callback` (`agent_model.py:308-312`); automatic prompt-caching injection (Anthropic `cache_control: "5m"`, OpenAI `prompt_cache_key=<project_id>` — `agent_model.py:217-236`); streaming-usage fixes (`stream_options.include_usage`, `agent_model.py:38-53,271-284`); browser agent forced `parallel_tool_calls=False` (`agent_model.py:246-258`).

**Two execution modes.** (1) *Workforce*: `Workforce(BaseWorkforce)` (`app/utils/workforce.py:64-107`) — coordinator/task agents from CAMEL, `TaskChannel`, 60-min task timeout, `failure_handling_config(["retry","replan"])`, quality re-analysis with 3 retries (`workforce.py:109-173`). Decomposition is split into `eigent_make_sub_tasks` (streaming decomposition, dependency updates, content validation) and `eigent_start` — which **clears pending tasks to honor the user-edited subtask list** ("tasks may have been added during decomposition before user edits", `workforce.py:248-252`). Workers join via `add_single_agent_worker` (rejected while running; workers share the workforce pause event — `workforce.py:627-654`). (2) *Single agent*: `single_agent()` (`app/agent/factory/single_agent.py:46-122`) — one root `Agents.single_agent` with `AgentRuntimeConfig(role, depth, max_depth=1 → can_delegate)`, all toolkits assembled via `assemble_single_agent_toolkits`; delegation through `remote_sub_agent_toolkit`/`depth_limited_agent_toolkit`. Memory service shares recovery helpers "by Single Agent and Workforce paths" (`app/memory/service.py:114-117`).

**Worker roster** (fixed, prompt+toolkit packages; `app/agent/README.md:83-90`): browser = "Senior Research Analyst", developer = "Lead Software Engineer", document = "Documentation Specialist", multi_modal = "Creative Content Specialist", mcp = "MCP Server Agent", social_media = "Social Media Manager", plus `question_confirm`, `task_summary`. Prompts in `app/agent/prompt.py` (44 KB, incl. `SINGLE_AGENT_SYS_PROMPT`, `MCP_SYS_PROMPT`). The frontend mirrors the roster with per-worker toolkit bundles in `BASE_WORKFLOW_AGENTS` (`src/components/WorkFlow/baseWorkers.ts:16-82`) and maps `single_agent: 'CAMEL Agent'` (`src/store/chatStore.ts:2249-2256`).

**Workforce UX & workflow canvas.** The React Flow canvas is an effectively **read-only visualization** of the workforce: `edges={[]}` always, an edit-mode flag exists but its setter is never called (`src/components/WorkFlow/index.tsx:61,333-345`), and nodes are auto-laid-out in a single row from live `taskAssigning` + `BASE_WORKFLOW_AGENTS` + `workerList` (`:195-200,224-238`), with per-task status filters on custom nodes (`src/components/WorkFlow/node.tsx:74-115`). "Workflow" is a workspace **view name**, not a saved artifact (`Task.activeWorkspace` defaults `'workflow'`, `chatStore.ts:1298`; no workflow save/load store) — the user-facing automation feature is **Triggers** (`src/types/index.ts:144-230`; `ExecutionType` scheduled/webhook/Slack; `useTriggerStore` with its own WebSocket connection status — the renderer WebSocket serves triggers, not chat). Mode selection is a single cycling button `ProjectModeToggle` over `ProjectMode = 'single-agent'|'workforce'` (`src/components/Workspace/ProjectModeToggle.tsx:70-90`; `src/store/projectStore.ts:123`) with live re-inference from task events (`src/lib/sessionMode.ts:55-84`); the chosen mode rides as `session_mode` in `POST /chat` (`chatStore.ts:2130-2147`); users add live workers mid-task via `POST /task/{id}/add-agent` (`src/components/AddWorker/index.tsx:607`); worker list persists per key in `authStore.workerListData` (`src/store/authStore.ts:103`).

**Orchestration bus.** `app/service/task.py` defines ~30 `Action*Data` models (Ask, CreateAgent, ActivateAgent, AssignTask, Terminal, TodoState, Notice, SearchMcp, InstallMcp, WriteFile, Stop, End, Timeout, Supplement, Add/Remove/SkipTask, DecomposeProgress/Text…) drained per-project under `get_task_lock(project_id)` (`task.py:87-303`). This is an **in-memory command/notification bus**, not a durable event log — nothing in the read paths reconstructs state from it.

**Tools & MCP.** ~40 built-in toolkits (`app/agent/toolkit/*`): `hybrid_browser_toolkit` (CDP-over-WebSocket connection pool — `hybrid_browser_toolkit.py:578,711-761`), `terminal_toolkit`, `file_write_toolkit`, `search_toolkit`, `rag_toolkit`, `human_toolkit` (ask-user), `skill_toolkit`, `observable_todo_toolkit`, `screenshot_toolkit`, `pyautogui_toolkit` (computer use), `code_execution_toolkit`, `web_deploy_toolkit`, office/social toolkits (Excel, PPT, Gmail/Notion/Lark/Slack/LinkedIn/Twitter/WhatsApp/Reddit), `remote_sub_agent_toolkit`, `mcp_search_toolkit`. MCP: a **dedicated MCP agent** aggregates every user-installed server's tools via `get_mcp_tools(options.installed_mcp)` plus MCP search; install endpoints `/mcp/install`, `/chat/{id}/install-mcp` (`app/agent/factory/mcp.py:31-87`; `app/controller/mcp_controller.py:30-36`). CAMEL `ToolkitMessageIntegration` routes tool messages to the human toolkit when remote sub-agents are on (`mcp.py:37-43`). Config shape `{command, args, description?, env?} | {url}` persisted in `~/.eigent/mcp.json` (`electron/main/utils/mcpConfig.ts:19-31`); UI = Connectors pages (`src/pages/Connectors/MCPConfigDialog.tsx` etc.) over Brain REST `mcpList/Install/Remove/Update` (`src/api/brain.ts:28-51`, "No IPC fallback") with Electron IPC twins retained (`electron/main/index.ts:1473-1514`).

**Skills & files.** Skill server: config/init/toggle/import/list/files routes (`app/controller/skill_controller.py:44-216`) + `skill_toolkit`; UI = `src/pages/Agents/Skills.tsx` with zip import + conflict list (`src/api/brain.ts:75-94`); Electron seeds bundled examples into `~/.eigent/skills` and passes `EIGENT_EXAMPLE_SKILLS_DIR` to the backend, with an explicit "all operations via Brain REST API (backend). No IPC" (`electron/main/index.ts:1706,2331-2493,3161-3172`); org repo `eigent-ai/agent-skills` exists (GitHub org). Artifacts: produced files arrive via SSE `write_file` → per-task file list (`src/store/chatStore.ts:3586-3592`), listing/preview via `app/controller/file_controller.py:92-344` (path pattern `/{email}/{project_id}/{file_path}`), opening via Electron `open-file`/`localfile://`; `web_deploy_toolkit` deploys outputs as web pages.

**Human-in-the-loop & security.** Escalation = `HumanToolkit.send_message_to_user` → `ActionAskData` → `/chat/{id}/human-reply` (`chat_controller.py:788`); UI-side, SSE `ask` sets an `activeAsk` queue, answers typed in the chat input post to the dedicated endpoint (`src/components/ChatBox/index.tsx:762-768`), and `wait_confirm` is the mid-task confirmation state (`src/store/chatStore.ts:4183-4238`). Plan confirmation drives execution: `handleConfirmTask` → `PUT /task/{id}` → `POST /task/{id}/start` with a **30s auto-confirm timer** (`chatStore.ts:2574-2627,4681-4754`); stop = backend `skip_task` with sentinel `'<summary>Task stopped</summary>'` (`:3857-3862`). An approval-mode picker exists but ships **unwired**: `ApprovalMode = 'manual'|'skip'` is "UI only for now… not wired to the human-toolkit / approval backend" (`src/components/ChatBox/BottomBox/ApprovalModeSelect.tsx:15-22,34-45`). **No permission engine, no tool-risk classification, no OS sandbox, no guarded tool pipeline found anywhere in the local runtime** — gating is ask-based only. Telemetry: `WorkforceMetricsCallback` exports workforce spans via OTLP (`app/utils/telemetry/workforce_metrics.py`).

## 3. Distinctive capability analysis (DSH comparison)

Format: **capability** — mechanism (evidence) → DSH relationship (classes: Equivalent / Packaging gap / Plugin opportunity / Core gap / Not applicable).

- **D8 Specialist workforce w/ editable task tree** — planner decomposes to user-editable subtasks, TaskChannel assignment, retry/replan (`workforce.py`) → **Packaging gap** *(provisional: DSH workflow scripts + agent-team DAG could compose this, but nothing productizes planner→worker trees with mid-flight edit)*.
- **D8 Pause/resume of a running workforce** — shared pause events, worker add blocked while running (`workforce.py:627-654`) → **Packaging gap** *(provisional)*.
- **D3 Consumer-app toolkits as stock tools** — Gmail/Notion/Slack/LinkedIn/Excel/PPT etc. in-tree → **Packaging gap** (DSH composes these as MCP servers; none shipped).
- **D3 MCP marketplace/search + one-click install** — `McpSearchToolkit`, `/mcp/install`, Electron `mcpConfig.ts` → **Packaging gap**; the search/discovery piece alone is a **Plugin opportunity** *(provisional: DSH plugin over a catalog API)*.
- **D12 Browser automation + computer use + persistent login state** — CDP pool, pyautogui, screenshots, `/browser/login`, cookie domains (`tool_controller.py:143-1165`) → **Core gap** (DSH deliberately has no browser/screen tools; new tool families + a browser-control seam would be needed).
- **D13 Ask-based escalation (no permission engine)** — HumanToolkit + human-reply + chat-answer flow → **Equivalent** (DSH `ctx.approval` + `ask_user_question`, strictly stronger: one-shot grants, deny policy, audit pair); the shipped approval-mode picker is an unwired UI stub → Not applicable.
- **D9 Triggers (scheduled/webhook/Slack automation)** — `Trigger`/`TriggerExecution` with `ExecutionType scheduled|webhook|slack`, trigger-only WebSocket subscription (`src/types/index.ts:144-230`; `src/store/triggerStore.ts:37-41,90`) → **Packaging gap / Core gap torn (provisional)**: opt-in `dsh-schedule` covers timed reminders only; the webhook and chat-platform trigger legs would need channel seams DSH deliberately lacks.
- **D16 Desktop shell owning agent-runtime lifetime** — Electron spawns/self-repairs the uvicorn backend (prebuilt venvs, health-poll, tree-kill teardown), injects port via IPC → **Packaging gap** *(provisional: DSH has Electron file://+IPC builds and host plugins, but no packaged "shell supervises runtime" story)*.
- **D5 Credits/proxy subscription runtime** — cloud proxy URLs, hot model reload via callback (`agent_model.py:125-150,308`) → **Not applicable** (SaaS billing layer, not harness capability).
- **D8 Remote sub-agent providers** — `app/remote_sub_agent/providers` + `/remote-sub-agent/validate` → **Equivalent** (DSH subagent seam incl. external-harness providers codex/claude/acp).
- **D4 Skill server with toggle/import** — `skill_controller.py` → **Equivalent** (DSH `skill-filesystem` layered roots; mechanism differs: HTTP API + frontend toggle vs fs discovery).
- **D19 Workforce OTel metrics** — `WorkforceMetricsCallback` → **Equivalent** (DSH `session-telemetry-otel` capture/redact waterfall).
- **D16 Desktop shell owning agent-runtime lifetime** — Electron spawns Python backend, injects port; PTY + webviews in main process → **Packaging gap** *(provisional: DSH has Electron file://+IPC builds and host plugins, but no packaged "shell supervises runtime" story)*.
- **D18 Deliverable preview/deploy** — `/files/preview/...`, `web_deploy_toolkit` → **Equivalent** (DSH deliverables surface + attachments); web-deploy itself **Packaging gap** *(provisional)*.

## 4. Absences (DSH has, Eigent lacks)

No plugin/extension architecture (fixed roster, no seams, no package distribution); no durable event-sourced session log — no fork/resume/replay/search over one stream (in-memory Action bus + files); no guarded tool pipeline (no pre/post policy, deny-only guards, frozen args); no file-effect sandbox or OS confinement; no permission presets/risk classes; no headless one-shot/SDK/ACP embedding channels; no goal model; no cron/reminder scheduling; no KV-cache-stability discipline (cache defaults exist but no documented invariant). Inverse absences (Eigent has, DSH lacks) are the Core-gap/Packaging-gap rows above — browser/computer use, stock consumer toolkits, workforce UX, MCP marketplace.

3. Unread surfaces (extraction lost the checkout mid-task): artifact-viewer component internals (per-task file list + `Session/PreviewPanel` verified; a "deliverable" concept unconfirmed), MCP dialog field list, Skills page body, trigger WS URL origin, TaskState UI components.
