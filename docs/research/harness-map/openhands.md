# OpenHands profile: architecture & capability surface

**Baseline for: Agent Harness Capability Map (profile #12 of 18)**

**Verdict.** OpenHands (2026 shape) is not one harness but a **four-repo fleet platform**: a Python Software Agent SDK (frozen-pydantic agents, event-sourced conversations, tool registry) whose canonical deployment puts a **whole agent server inside the sandbox container**, a React "Agent Canvas" control center that treats local/Docker/VM/cloud backends — and even Claude Code/Codex/Gemini via ACP — as interchangeable, an OpenAPI-generated TypeScript client as the contract, and a separate cron/webhook automation service. Its action/observation event log shares DSH's core bet (the log is the source of truth; LLM messages are a projection, `deriveMessages` ≡ `events_to_messages`) but goes further in one axis — the log is a **tree** with `navigate_to` re-heading and `llm_response_id`-grouped parallel calls — while lacking DSH's runtime *assertion* of the model-visible-from-log invariant. The deepest architectural divergence from DSH is the isolation model: OpenHands has no in-process file-effect sandbox at all (container-or-host, risk handled by an unusually deep confirmation/analyzer stack that even embeds risk prediction in the tool schema), where DSH confines tools with OS runners inside one process. Its extension story is an **ecosystem-interop bet**: plugins, hooks (external processes with exit-code blocking, including denying the agent permission to stop), SKILL.md skills, and slash commands all follow Claude Code's formats, with SHA-pinned git distribution and a marketplace — complementary packages rather than DSH's orthogonal runtime seams. Distinctive vs DSH: the automation service (cron/webhooks/run history/A-B), multi-backend canvas with cross-instance conversation leases, browser automation with rrweb recording, an LLM-judged `/goal` loop, stuck detection, and end-to-end dollar-cost accounting; DSH retains the sharper in-process axes — graded sandboxing, typed-event interception, KV-cache discipline, in-session jobs, and third-party UI slots.

## 1. Positioning & repo layout

OpenHands (formerly OpenDevin; platform paper arXiv:2407.16741) restructured into a **multi-repo system** under the `OpenHands` GitHub org (renamed from `All-Hands-AI`; ticket's URL still resolves via redirect). "Repository boundaries" table (OH-App@b50c60c README): **OpenHands/OpenHands** = Agent Canvas, a "self-hosted developer control center for coding agents and automations" — React/TS frontend + `agent-canvas` npm launcher that boots a local stack (agent-server + automation backend + ingress); runs the OpenHands agent or **any ACP agent** (Claude Code, Codex, Gemini CLI) across local/Docker/VM/cloud backends. **OpenHands/software-agent-sdk** = the Python SDK + Agent Server ("agents, tools, conversations, workspaces, events, and the canonical server API"; SDK paper arXiv:2511.03690, "A Composable and Extensible Foundation for Production Agents", SWE-bench 77.6 badge). **OpenHands/typescript-client** mirrors the server API for browsers. **OpenHands/automation** = cron/webhook scheduling, dispatch, run history (FastAPI + PostgreSQL). Repo layout (SDK@b57ba44 tree): `openhands-sdk/` (framework), `openhands-tools/` (tool implementations), `openhands-workspace/` (workspace kinds), `openhands-agent-server/` (FastAPI) — one repo, four installable packages. Docs live at docs.openhands.dev (docs.all-hands.net is superseded; older SDK docstrings still cite it). V0→V1 restructure: legacy monorepo "runtime" docs moved to a Legacy tab; V1 renames runtime→sandbox (docs sandbox overview).

## 2. Agent SDK structure

- **Agent = frozen pydantic config**: `AgentBase` is "stateless and fully defined by their configuration" (`frozen=True`); fields: `llm`, `tools` (name+params specs), `mcp_config`, `filter_tools_regex`, `include_default_tools` (FinishTool, ThinkTool), `agent_context` (skills), `condenser`, `critic`, prompt preset. Concrete `Agent(CriticMixin, ResponseDispatchMixin, AgentBase)`; `step()`/`astep()` mutate `ConversationState` in place and stream via `on_event`/`on_token` callbacks. `ACPAgent` wraps an external ACP CLI subprocess as an agent (`agent_kind: openhands|acp`).
- **Conversation factory** picks implementation by workspace type: `LocalConversation` (loop in your process; 3.1k lines orchestrating plugins, hooks, security, compaction, fork/navigation) vs `RemoteConversation` (thin client to a server-hosted conversation). Config knobs: `max_iteration_per_run=500`, stuck detection, secrets, `client_tools` (UI-provided tools), observability span/tags.
- **LLM layer**: LiteLLM underneath; `LLMRegistry` keys LLM instances by `usage_id` with per-usage metrics isolation (condenser LLM ≠ agent LLM); `RouterLLM` = an LLM subclass wrapping `llms_for_routing` with an abstract `select_llm(messages)` — routing is an LLM-shaped object, not a config table; `fallback_strategy.py`; native vs converted function calling (`fn_call_converter`, `non_native_fc` mixins); OpenAI Responses + Anthropic thinking blocks both first-class in `Message`.
- **Identity**: `~/.openhands/SOUL.md` replaces the default agent identity in the system prompt; prompt presets (DEFAULT/PLANNING) + per-subclass Jinja escape hatch. Mid-conversation `switch_llm` tool + `switch_profile` (profile-named LLM slots, e.g. "oracle") + condenser swap on model switch.
- **Design stance** (paper + code): everything that crosses a boundary is a pydantic discriminated union serializable as pure JSON (`DiscriminatedUnionMixin` everywhere; tools resolve from `(name, params)` specs at runtime).

## 3. Event model: actions, observations, event streams

- **Event base** (`sdk/event/base.py`): frozen, `extra="forbid"`; `id`, `timestamp`, `source: agent|user|environment|hook`, and **`parent_id` — the log is a tree**, not a list: `navigate_to(event_id)` re-heads the branch, `path_to_root()` walks the active branch (cycle-checked; legacy events fall back to linear chain). `EventType = action | observation | message | system_prompt | agent_error`.
- **ActionEvent**: `thought`, `reasoning_content`, `thinking_blocks`, `responses_reasoning_item`, executable `action` vs raw `tool_call` (kept separately — may carry LLM-predicted `security_risk`), `llm_response_id` (groups parallel tool calls from one response), `security_risk`, `critic_result`, and a ~10-word LLM-written `summary` for explainability.
- **ObservationEvent**: tool result + `action_id` backref + `extended_content` (path-scoped rule injections appended after the result — cf. DSH context injection). `UserRejectObservation` records rejections with `rejection_source: user|hook`. `AgentErrorEvent` carries `ErrorClassification(FailureKind, retryable)` — cf. DSH canonical failure codes.
- **Projection** (`events_to_messages`): read-only fold of the event log into LLM messages — batches ActionEvents by `llm_response_id` (reconstructs one assistant message with N tool_calls), coalesces adjacent plain user messages. Direct analog of DSH `deriveMessages()`; the DSH "model-visible ⇒ reconstructable from log" runtime invariant has no asserted counterpart here (convention, not enforced — inference from absence).
- **EventLog** (`conversation/event_store.py`): **one JSON file per event** (`event-<idx>-<id>.json`) on a `FileStore` abstraction (local / in-memory); `FileStore.lock()` gives thread+process safety (30s timeout; documented NFS caveat); append validates parent existence and duplicate ids; stale-index rebuild from disk. Streaming tokens travel a separate `on_token` callback channel (cf. DSH `assistant/chunk` vs `assistant/message`).
- **vs DSH (D1/D19)**: same event-sourced philosophy, materially different storage (per-event JSON files vs checksummed zstd JSONL frames), **in-log branching** where DSH forks a new session seeded with a prefix, and `llm_response_id` grouping where DSH uses turn/step container events.

## 4. Runtime & sandbox abstraction; Docker/remote execution

- **`BaseWorkspace` ABC** (`sdk/workspace/base.py`): `execute_command` (30s default), `file_upload/download`, `git_changes/git_diff`, **`pause()/resume()`** (pause a container to save resources), cost registration + automation completion callback (`AUTOMATION_CALLBACK_URL` POSTs status/run_id/cost on exit). `LocalWorkspace` runs on the host (Canvas quickstart warns: "the agent will have full access to your filesystem").
- **The sandbox is a full agent server**: `RemoteWorkspace` is an HTTP client; container kinds live in `openhands-workspace`: `DockerWorkspace` (pre-built `ghcr.io/openhands/agent-server` image; random port 30000-39999; health-check wait; volumes; GPU; optional VSCode/VNC ports; platform pinned `linux/amd64`), `DockerDevWorkspace` (builds image on the fly), `APIRemoteWorkspace` (**OpenHands Runtime API**, runtime.all-hands.dev: container lifecycle management with `resource_factor` 1/2/4/8, `runtime_class: sysbox-runc`, `keep_alive`, `pause_on_close`), `OpenHandsCloudWorkspace` (Cloud API provisioning; `local_agent_server_mode` when already inside a cloud sandbox), `ApptainerWorkspace` (HPC, no Docker daemon).
- **Two loop placements**: agent loop in your process with a remote workspace (LocalConversation), or the whole conversation server-side with a thin client (RemoteConversation) — the SDK's own framing (docs intro): run locally "or scale to 1000s of agents in the cloud".
- **Isolation model**: no OS-level file-effect sandbox in the SDK (nothing like DSH's bwrap/Landlock/Seatbelt/ACL runners or read-only/workspace-write modes) — isolation is the container boundary or nothing; risk is managed by analysis+confirmation (see §5 security) instead. Inference from module inventory; `defense_in_depth` operates on shell semantics, not file effects.
- **"Runtime plugins" (V0 meaning) are gone**: the old monorepo's runtime-plugin injection (Jupyter/AgentSkills requirements into the sandbox) has no V1 equivalent; V1 "plugins" are prompt/MCP/hook packages loaded into the agent (§5). Inference from repo layout + V0/V1 doc split.

## 5. Extensions/plugins, tools, MCP, security

- **Plugins = Claude Code plugin format** (`sdk/plugin/`): `.claude-plugin/plugin.json` (or `.plugin/`) + `skills/` + `hooks/hooks.json` + `.mcp.json` + `agents/` (subagent definitions) + `commands/` (slash commands, converted to keyword-triggered skills namespaced `/plugin:command`). Merge semantics: plugin skills/MCP servers override same-named existing ones (warned). `PluginSource` = `github:owner/repo` | any git URL | local path, with `ref` and `repo_path` (traversal-validated); **`ResolvedPluginSource` pins the commit SHA** so pause/resume re-fetches the exact version; URL credentials redacted in persisted state. Installed lifecycle: `~/.openhands/plugins/installed/.installed.json` `enabled` flags; CLI `/plugin install|enable|disable|uninstall` on SDK APIs. Migration to the agent-plugins.org portable format is specced (issue #4405) — format in flux.
- **Marketplace**: `sdk/marketplace` + the `OpenHands/extensions` repo (public registry; `marketplaces/openhands-extensions.json`); `AgentContext(load_public_skills=True)` auto-loads public skills (uv, deno, …) keyed on repo markers.
- **Hooks = external processes** (`sdk/hooks/`): Claude Code-compatible events `PreToolUse / PostToolUse / UserPromptSubmit / SessionStart / SessionEnd / Stop`; hook scripts get a JSON `HookEvent` on stdin; exit 2 blocks (`HookDecision: allow|deny`; "ask" is future). A `Stop` hook can **deny the agent permission to finish** — the run loop injects the hook's feedback as an environment message and continues. PreToolUse blocks surface as `UserRejectObservation(rejection_source="hook")`. This is the interception seam — out-of-process scripts, not in-process typed events (contrast DSH `waterfall` interception).
- **Tools** (`openhands-tools/`): `ToolDefinition` = Action/Observation pydantic pair + annotations + executor; registry maps name → `create(conv_state, **params)` factory with `is_usable()` platform gating and optional `response_schema` (structured output). Stock: **TerminalTool** (persistent session; tmux preferred, subprocess-PTY fallback, Windows terminal; tmux pane pool; soft timeouts; client env hidden from the model-facing schema), FileEditor/apply_patch/glob/grep, **BrowserUseTool** (Playwright-class browser use with rrweb session recording), `delegate` (named subagents = child conversations, `max_children=5`, child-confirmation bridging handler), `workflow` (model-written **Python** `async def main(wf)` scripts, `max_concurrency` 1–64), task tracker, `ask_oracle` (second opinion from a saved "oracle" LLM profile — convention over wiring), `tom_consult`, builtins finish/think/invoke_skill/switch_llm/**vision_inspect** (auto-attached vision tool when the driving model can't see images but a vision profile exists).
- **MCP** (`sdk/mcp/`): `mcp_config` on Agent; tools auto-discovered; **`tools/list_changed` progressive disclosure handled live** (additions/replacements/conflict detection against runtime tools); server side has an MCP OAuth store. Resources/Prompts support unverified.
- **Security stack** (`sdk/security/`): `SecurityAnalyzerBase.security_risk(ActionEvent) → LOW|MEDIUM|HIGH|UNKNOWN` with analyzer failure defaulting to HIGH (fail closed); confirmation policies `AlwaysConfirm | NeverConfirm | ConfirmRisky(threshold, confirm_unknown)`; analyzers include shell-AST parsing, `defense_in_depth` (pattern, **policy rails**, shell semantics), a Grayswan-integration analyzer, LLM analyzer, ToolShield LLM analyzer, and an `ensemble`. Uniquely, the LLM can be asked to predict `security_risk` *in the tool schema*, stored on `tool_call` but stripped from the executable `action`. Runtime-togglable per conversation (`set_confirmation_policy`, `set_security_analyzer`, `reject_pending_actions`).

## 6. Persistence, scaling, client/server boundaries

- **SDK-side state**: `ConversationState` (execution_status machine IDLE/RUNNING/PAUSED/ERROR/STUCK/FINISHED/WAITING_FOR_CONFIRMATION; security knobs; activated skills/path rules; `agent_state` scratch) autosaved; secrets encrypted with a `Cipher` keyed by `OH_SECRET_KEY` (without it: redacted, lost on restart).
- **Agent Server** (FastAPI, ~20 routers: conversations, events, files, bash, git, vscode, desktop, skills, sub_agents, plugins, canvas_extensions, hooks, llm, provider_connections, mcp, settings, workspaces, profiles, auth + an **OpenAI-compatible endpoint**): file-based persistence (settings/secrets/workspaces stores with fcntl/msvcrt locking); README depicts `conversations/<id>/metadata.json + events.jsonl`.
- **Cross-instance coordination** (`conversation_lease.py`): `owner_lease.json` holds owner instance id, monotonic `generation`, 45s TTL; takeover fences stale owners (`ConversationOwnershipLostError`), PID-liveness checks — multiple agent-server instances can share storage safely. `fifo_lock` orders concurrent user messages. `PubSub` fans events out concurrently to WebSocket subscribers (`/events/socket`), webhooks (buffered, retried), telemetry.
- **Scaling model**: "a REST API for running multiple agents on a single machine" (OH-App README); scale out = more containers (Runtime API `resource_factor` scales a container up); Canvas **switches between multiple agent servers** from one UI; leases make shared-storage multi-instance safe; Cloud/Enterprise run it on Kubernetes (RBAC, budgeting = commercial).
- **Client boundary**: TypeScript client generated from the server's OpenAPI contract ("SDK/Agent Server → OpenAPI contract → typescript-client → Agent Canvas"); Canvas holds no credentials — the server owns subprocesses and secrets, the browser sends `LookupSecret` references resolved server-side at spawn; `server_info.runtime_services` is forwarded into new conversations as agent-context suffix so the agent knows service URLs.
- **Observability**: three deliberately separated planes — product telemetry (PostHog/HTTP exporter; consent-respecting, allowlisted events, bucketed magnitudes, `DO_NOT_TRACK` kill switch), **LLM completion logging** (full fidelity, local disk only), and OTel/Laminar distributed tracing (`@observe` spans). Nothing from the latter two reaches telemetry.
