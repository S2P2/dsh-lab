# Cloudflare OS profile: capability surface vs the DSH baseline

**Verdict.** Cloudflare OS (`cloudflare/cloudflare-os`, open-sourced Aug 4–5 2026) is not a harness you install next to your other tools — it is an Access-fronted, multi-user *product* whose every architectural decision assumes the Cloudflare runtime: each workspace is a stateful kernel Durable Object, each agent-built "Gadget" runs as a Dynamic Worker Facet with its network reach defined purely by injected bindings, and all external access flows through per-service **Gatekeeper** Workers that hold credentials, log every read ("observation"), and replace synchronous human approval with *simulated* outcomes plus a deferred approval queue. Its distinctive center of gravity is **object-capability security enforced by types and topology** (role-derived RPC interfaces where adding a method fails compilation until someone decides who may call it; a mediator Worker that owns secrets outside the app's process), which DSH cannot replicate by packaging because DSH's guards and approvals attach to *tool calls*, not to *resources mediated out-of-process*. Inversion worth starring: the CFOS agent has **no shell tool at all** — it works by writing TypeScript snippets (`executeCode`) against typed APIs, while DSH's stock catalog centers on bash/pwsh. Absences are loud in both directions: CFOS has no plugin/composition ecosystem (extension = fork the product), no headless/API channel, no OTel telemetry seam, and no in-session delegation depth — while remaining the cohort outlier on multi-user sharing (permission graph with lazy revocation, per-observer information-flow re-verification).

## 2. Runtime substrate & "kernel" composition

- Everything runs on Workers; "heavy use of Durable Objects, **Dynamic Workers**, and **Facets**: **every workspace is its own Durable Object, every Gadget runs in a Dynamic Worker Facet, and Gatekeepers also install facets into each workspace**" (README §Built on Workers). Features were "added to the runtime specifically to support Cloudflare OS" (same section; consistent with the platform timeline above: Dynamic Workers beta 2026-03, Facets 2026-04, OS release 2026-08).
- Kernel code: one `workshop-backend` Worker; per-workspace `OverseerDurableObject` (SQLite-backed DO, wrangler migrations v0–v2: `UserDurableObject`, `OverseerDurableObject`, `AdminSettings`, `PendingLogin`). Facets instantiated by name from the workspace DO: `this.ctx.facets.get(\`gadget${id}\`/\`gatekeeper${id}\`, factory)`; killed via `ctx.facets.abort(...)` (src/overseer.ts @1411714, grep verified).
- Transport: Cap'n Web RPC everywhere — browser⇄backend over one persistent WebSocket (`api.ts` interface is the contract), gadget iframe⇄parent over `postMessage()`. Repo-wide conventions: promise pipelining, `@validateRpc()` runtime type validation, explicit stub disposal (AGENTS.md "IMPORTANT" blocks).
- Edge router Worker (`packages/router`) is the public origin; routes `/api/*` to backend and `/gatekeeper/<name>/*` by scanning its own `GATEKEEPER_*` service bindings — "installing a gatekeeper is purely a binding change" (AGENTS.md §router).
- In-progress model shift (`plans/multi-gadget.md`): v1 shipped workspace=gadget=one Overseer DO; the plan migrates to numbered **workpieces** (gadgets + gatekeepers in one ID namespace, per-workpiece Yjs roots, agent `createGadget`, workspace-scoped chats editing many gadgets). HEAD already shows per-id facet helpers and `WorkpieceSummary.chatId` in sharing docs — treat plan-vs-shipped boundary as *ambiguous at a fast-moving HEAD* (see §11).

## 3. Workspace & agent execution

- **Agent loop**: Pi stack — `@earendil-works/pi-agent-core` `runAgentLoopContinue` (migrated off Vercel AI SDK), `toolExecution: "sequential"`, **turn cap 30** (`shouldStopAfterTurn`), pi-managed Anthropic prompt caching (`cacheRetention: "short"`), two-slot system prompt concatenated static-first "to preserve prefix stability" (plans/pi-impl.md §1 — design doc, code-consistent naming throughout agent.ts).
- **Chat-agent tool inventory** (from `src/agent.ts` registrations): `readFile`/`writeFile`/`editFile` (workpiece-scoped, read-before-edit tracked per `(workpieceId, filename)`), `webFetch`, `observeUserChanges`, `describeBinding`, `setGadgetBinding`, `createGadget`, `listBlueprints`, `executeCode`, `listConnectableResources`, `requestConnection`, `giveUp`. **No shell, PTY, or computer-use tool.** `executeCode` = Code Mode: agent writes TS/JS against typed API surfaces (gadget Cap'n Web APIs + named chat bindings via `getSession`/`getAgentCatalog`), executed in controlled contexts; streaming edits surfaced to the UI via `(workpieceId, filename)` events (plans/multi-gadget.md §agent).
- **Durability**: chats/messages/tool-calls persist in Overseer DO storage; resume **replays by re-running persisted tool calls** with creation re-adoption ("crashed-turn re-adoption", replay locks, revert elision — plans/pi-impl.md §2 "Invariants"; orphaned pending-gadget creations reconciled by `reconcilePendingGadgets()`, plans/multi-gadget.md Q15; step transactionality has its own plan doc). Compaction module `src/agent-compaction.ts` (checkpoint logic, summarization call) — closest analogue to DSH pressure compaction, far less documented publicly.
- Suspension/resume of long-running agent work uses DO hibernation (`awaitDecision` suspension listed as invariant; agent turns restored in DO constructor — overseer.ts:879-900 cited by the plan).
- Model/provider plane: Pi providers over HTTPS only; Cloudflare AI Gateway /compat endpoints, Workers AI REST, BYOK unified billing with compound `{provider}/{model}` ids; suggested-model catalog authoritative for compaction budgets (plans/pi-impl.md §§1.7–1.10, 4; src/ai-models.ts, ai-gateway.ts exist at HEAD). `nodejs_compat` enabled because provider SDKs + Puppeteer need it.
- Incidental capabilities: `BROWSER` binding (Browser Run API; local Chrome emulation in dev, remote on Cloudflare), Puppeteer for Gadget PDF exports (wrangler.jsonc compat-flag comments; src/browser-export.ts), `webFetch` hardened by `global_fetch_strictly_public` (wrangler.jsonc comment explains SSRF rationale; standalone workerd blocks private IPs by default; dev mode deliberately exempts localhost).

## 4. Gadgets: what generated apps ARE

- A Gadget is **a private per-user instance of an application** ("when you create a slide deck… the system creates a private instance just for you"), replacing SaaS centralization: safe to let anyone modify the code because instances are isolated (README §Gadgets).
- **Confinement, server side**: runs in a Dynamic Worker **with internet access disabled**; egress only via explicitly designated **Workers Bindings** (README §Sandboxed and secure by default). **Client side**: sandboxed iframe, `Content-Security-Policy`-restricted, speaks **only** a Cap'n Web RPC session handed over `postMessage()` (same section).
- Gadget ⇄ agent contract: because client/server must talk Cap'n Web, "every app …automatically has an agent-friendly API" — the harness exposes the gadget API directly as invocables (README §Collaborate with AI).
- Lifecycle: editing happens **only inside chats**; each chat holds proposed changes as Yjs updates against its own merged commit; accepting merges = fast-forward of mainline head; diverged mainline is reconciled by diff3 merge delivered *back into the chat* with inline conflict markers (plans/git-storage.md "Locked decisions"). Committed code lives as a **real git object store (SHA-1 loose objects, objects-only, no refs) inside the workspace DO** via isomorphic-git fs-shim; Yjs survives only as the *uncommitted*-changes representation (same doc; credits confirm isomorphic-git for gadget storage + future external-git/gatekeeper-gated push-pull). Changing a gadget's committed code aborts only its facet (`bumpVersion()` abort per affected gadget).
- Real-time collaboration built-in: presence/multiplayer "implemented by default" on Durable Objects; CodeMirror provides OT text editing (README §Real-time Multiplayer, Credits).

## 5. Gatekeepers & the capability/security model

- Anatomy: one service-specific Worker per vendor (17 shipped incl. github/google/cloudflare/notion/confluence/slack/supabase/email/homeassistant/linear/spotify/zoominfo/mcp/mcp-portal/context/scheduler); wraps the native API in a Cap'n Web API, handles OAuth, **enforces narrow per-resource scope**, logs every action (observations), mediates human approve/deny (README §Gatekeepers; AGENTS.md package list).
- **Zero-capability default**: "Each agent, and each Gadget, by default has access to nothing." Resources enter by *introduction* (paste link / add-resource UI); the agent may *request* an introduction which the user grants or denies — positioned explicitly against "MCP servers configured upfront" ambient access (README §Capability-based access control; press release: "AI agents start with zero permissions"). Kernel rule: "a resource becomes 'ambient' only by user/admin configuration — a gatekeeper must never assert its own ambience" (AGENTS.md kernel note).
- **Simulate-and-queue approvals** (the flagship review-difference): requiring synchronous approval makes users auto-approve everything; instead the Gatekeeper *simulates the outcome locally*, tells the agent it completed (with simulated read-backs), lets it keep working, and queues the real action; the human approves/rejects later in bulk or one-by-one (README same section). Queue execution details at HEAD: pending actions drain in id order; eligibility needs **both** signals (author's `autoApprovable` verdict AND a user-enabled `${gatekeeperId}:${actionKind}` rule); drain **stops at the first manual-gate action** rather than skipping past a human checkpoint; auto-applied actions are attributed to the enabling user (src/auto-approval.ts, whole file read).
- **MCP as gatekeepers**: `gatekeeper-mcp` (user-pasted endpoints) and `gatekeeper-mcp-portal` (admin-configured portal) share `mcp-shared`; trust boundary: `readOnlyHint: true` ⇒ runs as an observation, everything else queues for approval, and *auto-applying writes additionally requires a "vetted" endpoint which only the portal can produce* (`MCP_PORTAL_TRUST_ANNOTATIONS`) (AGENTS.md §mcp-shared).
- **Credential custody**: OAuth flows + tokens live inside the Gatekeeper/account DO; consumers get capabilities, not creds ("Gatekeepers hold credentials, enforce policy, record what was read, and mediate actions" — os.cloudflare.app; press/blog echo "Keys stay home"-style framing). Account capability, once minted, is the authority thereafter (AGENTS.md §gatekeeper-* provisioning bullets).
- **Observer information-flow control** (most novel layer): when a non-owner opens a shared gadget, they must connect *their own* account per relevant gatekeeper, which verifies — via `addObserver(observerId, verifier)` — that they could directly read **everything the gadget has ever read** through it; thereafter any new observation some authorized observer lacks privilege for is *blocked* (`excludeObservers`) unless that observer has lost access; checks re-run at every open; per-resource strategies: **A** private-only, **B** ACL-unit check, **C** observed-data-set tracking (BigQuery datasets, Linear teams, Notion pages…), **D** low-stakes no-op — with a per-gatekeeper decision table (docs/observers.md; fallback `prohibitAllSharing` lockdown remains for maximally-sensitive reads).
- Typing as enforcement: `open()` computes effective role and returns either the full `OverseerClientInterface` or a `UseOverseerInterface` that **implements the entire interface but throws `Unauthorized` outside a small allowlist** — "any newly-added interface method fails to compile until a developer consciously decides whether `use` callers may invoke it (default-deny)" (docs/sharing.md §Restricted capability).

## 6. Company context

- **Context Library gatekeeper** (`gatekeeper-context`): collections of context documents authored via management UI; agents receive a singleton read session as an ambient chat binding and **each read is recorded as an observation**; visibility split private (owner) vs **public (admin-curated, auto-enabled for everyone)**; state in three DOs + KV, namespaced by `sharingDomain` so several workshops can share one gatekeeper (AGENTS.md §gatekeeper-context).
- Deployment-level persona knobs: `AdminConfig` (admin `/panel`): agent instructions, banners/theme, offered connectors/resources, auto-provisioning modes (disabled/optional/enabled), promoted output formats (§7); mirrored to reserved KV key `.adminConfig` with DO-single-writer; auth config deliberately kept out of DB-reachable admin surfaces (env-var driven) so a compromised admin session can't change sign-in (AGENTS.md §Deployment admin settings).
- Marketing/positioning frames the same thing as grounding agents in organizational "terminology, policies, ways of working" (os.cloudflare.app; blog.cloudflare.com/cloudflare-os).

## 7. Blueprints & code distribution

- Blueprint = shareable snapshot of a gadget's **code** (committed Yjs doc stripped of history → stored as Yjs v2 document in R2 `BLUEPRINT_CONTENT/<id>/<version>`), plus **binding requirements** (type: gatekeeper / aiModel / agentSpawner, with annotations like suggested resource URL) and metadata (title/description/author/version); explicitly excludes SQLite contents, chat/edit history, creds (docs/blueprints.md; supersedes earlier web-index fragments).
- Storage chain Gadget DO → User DO → public **KV** (`BLUEPRINTS`, keyed by 128-bit hex id) with a `dirty`-flag retry protocol; view-without-auth via `/blueprint/<id>` link; creating requires auth; versions retained in R2 for concurrent-instantiation races; author updates bump versions — **no auto-update flow to existing instances** (docs/blueprints.md).
- Exchange format: `.gadget` binary container (magic `0xec2e2d3a2300e317`, version u32, JSON-metadata length, raw content length, metadata ≤64 KiB, payload ≤32 MiB import caps; streamed to/from R2 via `pipeTo()`); import re-roots into the importing deployment under importer ownership, preserving original author metadata; library entries saved-by-reference vs uploaded copies; Explore page = admin-featured blueprints (docs/blueprints.md; internal layout documented end-to-end).
- **Formats**: ordinary blueprints the deployment *promotes* so "+ New Doc"/"+ New Slides" appear in the composer and the agent is told to prefer them (`AdminConfig.formats`); five-ish shipping format-blueprints committed as data in `format-blueprints/` with stable ids (`format.document`), restorable/replaceable via `pnpm import:format-blueprint`, `FORMAT_BLUEPRINTS_DIR` override for forks; "never edit a `blueprintId` after deploy" (AGENTS.md §format-blueprints; docs/blueprints.md §Output Formats).
- Generated *documents* ride the same rails (slides/decks/doc gadgets; PDF export via Puppeteer/browser-export).

## 8. Sharing, identity & multi-user lifecycle

- Roles `build > use` on collaborators; permission **graph** (user edges + share-link edges; owner implicit root; grant capped at sharer's effective role) with a fixed-point effective-role computation recomputed live at every `open()`; **lazy revocation** = sever edges, reachability denies the rest; undo-friendly (nothing cascades destructively); two-phase preview/confirm for removals; `keepUsers` re-rooting (docs/sharing.md §Permission graph onward).
- Share links: 128-bit key shown once, server stores only HMAC-SHA-256 (fixed domain-separated constant); redemption+open atomic in one RPC (`openGadget(id, shareKey)`) so pipelining proceeds; links are graph nodes supported by their creator — creator losing access transitively revokes the link (docs/sharing.md).
- Live sessions aren't re-checked per message — so removals/downgrades **restart the workspace DO** (`ctx.abort()`) after syncing the severed edge, forcing reconnect+re-auth; granting never strands (docs/sharing.md §Terminating live sessions).
- Per-user resource scoping despite shared artifacts: collaborator AI chats bill to whoever prompted; bindings connect through the *creator's* connected accounts (`clientUser.getGatekeeperClassFor()`); no collaborator implicitly reaches another user's third-party accounts (docs/sharing.md §Resource isolation).
- Identity/lifecycle: password login or OAuth sign-in *through authentication gatekeepers* (`AUTH_GATEKEEPERS`, `PendingLogin` bridging DO — wrangler migrations v2 comment); admins via `ADMINS` binding (+AdminApi capability checked once at mint); enterprise deploys front with Cloudflare Access ("Access-mode frontend asset build" in the release pipeline; press release bullet "Zero Trust by Default: …built on Cloudflare Access"); releases ship as manifests with `$PLACEHOLDER`s → R2 content-addressed candidates → single promote copy, driven from GitLab CI (AGENTS.md §Release pipeline).
