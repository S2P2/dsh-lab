# thClaws: architecture & distinctive capabilities (vs DSH baseline)

**Baseline for: Agent Harness Capability Map (profile #20 of the cohort, post-synthesis extension)**

**Verdict.** thClaws (ThaiGPT Co., Ltd., Thailand; started April 2026, ~weekly releases, v0.116.0 at pin) is a **single-crate native-Rust agent workspace** whose defining bet is "one engine, four surfaces": one `Agent` + `Session` + `ToolRegistry` triad in one binary backs a wry+tao desktop GUI (React compiled to a single HTML file embedded via `include_str!`), a CLI REPL, a one-shot print mode, and an Axum `--serve` webapp — unified by a transport-agnostic `ipc::handle_ipc(msg, ctx) -> bool` dispatch shared verbatim between the wry IPC handler and the WebSocket server, plus a headless schedule daemon, subprocess teammates, and chat-channel adapters as further "just another mode against the same `.thclaws/` state" processes. Where DSH composes capabilities as swappable Cordis config rows, thClaws composes them as **filesystem markdown conventions plus fixed Rust subsystems**: `SKILL.md`/agent-defs/plugins are Claude-Code-compatible directory formats (`.claude/` read as fallback everywhere); MCP tools funnel into the same `ToolRegistry` as built-ins; memory and KMS are frontmatter'd markdown directories the LLM maintains through sandbox-carve-out tools; `/dream` mines session JSONL into reviewable wiki pages. Deepest divergences from DSH: shipped persistent memory + KMS + dream consolidation (D7), a three-layer scheduler incl. native launchd/systemd daemon (D9), channel adapters shipping (Telegram direct; LINE/Messenger via relay) with **approval UIs rendered in-chat**, multi-process Agent Teams on filesystem mailboxes + git worktrees, MCP-Apps HTML widgets, and OS-keychain-first secrets. DSH leads structurally on: config-layered composition/capability seams (thClaws extension = fixed conventions, nothing swappable), log invariants (JSONL is replayable persistence but no "model-visible means logged" law), OS-confinement sandboxing (thClaws = in-process path validation only), and UI extensibility (closed React app, no slots/roster). Not an OpenClaw fork despite the `*Claw` name and shared dream/channels/daemon vocabulary — convergent product space, different shape (workspace-first single-project desktop vs always-on multi-channel gateway).

## Architecture profile

### 1. Runtime shape: four surfaces, one engine (D1/D16)
- Single crate `crates/core`; two binaries — `thclaws` (unified, GUI default) and `thclaws-cli` (no `gui` feature) [tm:app-architecture, running-modes]. GUI = wry+tao webview loading the embedded single-file React build through a custom `thclaws://` protocol (`/file-asset/<path>` sandbox-checked file serving); `--serve` = Axum (`GET /`, `/healthz`, `/ws`) serving the *same embedded frontend*, `useIPC.ts` auto-detecting `window.ipc` (wry) vs WebSocket [tm:app-architecture §5–6, serve-mode §1].
- Process model: main OS thread (tao loop) + one tokio worker thread owning `WorkerState` + translator thread + approval/ask-user/team forwarder threads; channel topology = mpsc `ShellInput` in, `broadcast<ViewEvent>(256)` out; Terminal and Chat tabs are *two renderings of one ViewEvent stream* ("single-conversation contract") [tm:app-architecture §3–4,7].
- The load-bearing seam: **`handle_ipc(msg, ctx) -> bool`** — 50 shared dispatch arms consumed by both wry and WS; GUI falls through to ~7 wry-only arms. Introduced as migration invariant M6.36 SERVE9 [tm:running-modes §6]. Print mode reached full surface parity in v0.88.0 (Task tool, session persist + `--resume`, hooks) [tm:running-modes §1].
- All modes share the project's `.thclaws/` state dir (sessions, KMS, memory, team, plugins, todos, hooks) — "the project folder is the deploy unit" [tm:serve-mode §6]. Known limits: single window/project per process; broadcast `Lagged` drops without resync [tm:app-architecture §15].

### 2. Provider abstraction & mid-session switching (D5)
- One `Provider` trait (`stream()` only mandatory) + closed 25-variant `ProviderKind` enum; model strings carry routing prefixes (`openrouter/…`, `zai/…`) detected by ordered prefix match; aliases (`sonnet`, Thai-model names) incl. a **provider-aware alias resolver** so teammate agent-defs never surprise-switch provider [tm:providers §2–4]. Wire formats normalized into a 7-variant `ProviderEvent` vocabulary; `<think>`-tag splitting with implicit-thinking pre-seed for Qwen3/R1-family [tm:providers §6].
- `build_provider_with_fallback` walks a preference chain at startup (500 ms Ollama probe) and degrades to `NoProviderPlaceholder` — app opens without keys [tm:providers §5]. Mid-session switch = `/model`, `/provider` → `WorkerState::rebuild_agent(preserve_history=true)` (provider/model/approver/cancel re-wired, history kept) [tm:app-architecture §4; tm:agentic-loop §2]. Skill frontmatter `model:` triggers a **per-turn auto-switch** when the key exists [tm:skills §1].
- Notable variants: `AgentSdk` (Claude Code `claude` CLI subprocess provider, 4-stage protocol, reusing Claude Code auth), `ChatGPTCodex` (OAuth auto-imported from `~/.codex/auth.json`), three Ollama shapes incl. Anthropic-compatible, ThaiLLM (OpenThaiGPT/Typhoon/Pathumma/THaLLE) [tm:providers §2; provider-agentsdk]. EE gateway overlay substitutes *all* cloud providers with one OpenAI-compatible gateway [tm:providers §4A; provider-gateway].

### 3. MCP, skills, plugins, hooks, marketplace (D3/D4/D2)
- **MCP client**: JSON-RPC 2.0, protocol `"2024-11-05"`; tools-only + `resources/read` (for widgets); no prompts/sampling. stdio + Streamable HTTP with **OAuth 2.1 + PKCE** (RFC 8414/7591/9728), **authorization-server binding** on cached tokens (blocks discovery-swap token reuse), mid-session 401 re-auth preserving `Mcp-Session-Id`, manual 307/308 redirect handling that keeps `Authorization`. Two budgets: 30 s requests / 300 s init (cold `uvx`/`npx` installs) [tm:mcp §1–3,6]. **stdio spawn allowlist** (`~/.config/thclaws/mcp_allowlist.json`, keyed by command string, approval-gated first spawn, atomic writes) [tm:mcp §4]. Tools register as `<server>__<tool>` sanitized-qualified names, bare name preserved for dispatch — same disambiguation scheme as DSH's `mcp__<server>__<rawName>` [tm:mcp §5].
- **MCP-Apps**: trusted servers ship interactive HTML widgets (`ui://` resources) rendered in sandboxed iframes in chat; host acts as JSON-RPC *server* over postMessage; widget→server tool calls go back through the approval gate. Trust ≠ unattended execution — two separate gates [tm:mcp §7].
- **Skills**: `SKILL.md` + `scripts/` + `requirements.txt`; 5-tier discovery (`~/.claude/skills` < `~/.config/thclaws/skills` < plugin dirs < `.claude/skills` < `.thclaws/skills`); lazy frontmatter-only discovery (4 KB cap, `OnceLock` materialization); three system-prompt listing strategies (`full`/`names-only`/`discover-tool-only`) = token-budget progressive disclosure; `/<skill-name>` user shortcut rewrites to a synthetic prompt through the agent loop; Python skills get an auto-venv layer in the Bash tool [tm:skills §2–7].
- **Plugins**: bundles of skills + prompt-commands + agent-defs + MCP servers under `.thclaws-plugin/plugin.json` (Claude Code `.claude-plugin/` fallback — anthropics-style plugins install unchanged); project/user scopes; install = git/zip with `#branch:subpath` monorepo fragments, staging + atomic rename, path-traversal-validated names; live refresh of skills/commands but **MCP subprocesses need restart** (tracked debt) [tm:plugins §1–6].
- **Hooks**: user shell commands on 8 lifecycle events (`pre_tool_use`, `post_tool_use[_failure]`, `permission_denied`, `session_start/end`, `pre/post_compact`); fire-and-forget with zombie reaper + 5 s SIGKILL timeout; env-var payload (≤8 KB); read-only observers, never mutators — explicitly *not* a gate [tm:hooks]. Honest history: dead code until M6.35.
- **Marketplace**: first-party curated `marketplace.json` served from thclaws.ai; three-layer load (embedded baseline via `include_str!` → user cache → explicit/daily-24 h remote refresh, validate-before-write, schema-version-gated); entries = skills/MCP/plugins; `license_tier: linked-only` lists but refuses install of source-available Anthropic skills [tm:marketplace §1–3].

### 4. Three-tier agent orchestration & Agent Teams (D8)
- Tier taxonomy, explicit in the manual: **TaskCreate** (in-memory scratchpad, no LLM) / **`Task`** subagent (in-process recursive `Agent::run_turn`, depth ≤ 3, spawn always requires approval, parent's approver/mode/cancel propagate; `.thclaws/agents/*.md` AgentDefs with tools allow/deny-lists, model + maxTurns overrides) / **`/agent` side-channel** (user-driven concurrent spawn on its own tokio task, fresh independent CancelToken, `AgentOrigin` tagging so approval modals say which agent asks, panic watchdog) [tm:subagent, side-channel].
- **Agent Teams** = the only out-of-process tier: `thclaws --team-agent <name> --accept-all` subprocesses per teammate, coordinating through JSON file mailboxes + per-task files with `blocked_by` deps under `.thclaws/team/` (file locks; `_hwm` id counter); 10 team tools (`TeamCreate`/`SpawnTeammate`/`SendMessage`/`CheckInbox`/`TeamStatus`/`TeamTask*`/`TeamMerge`); optional per-teammate **git worktree isolation** (`team/<name>` branches, `THCLAWS_PROJECT_ROOT` pins the sandbox to the parent workspace, cwd-relative writes land in the worktree); tmux split-window when available; typed protocol messages (Idle/Shutdown) embedded in inbox text; lead/teammate hard-blocked bash commands (destructive ops, cross-branch resets); `TeamMerge` stops on first conflict and suggests delegating the fix to the owning teammate [tm:agent-team §1–7].

### 5. KMS, persistent memory, `/dream` (D7)
- **KMS** = per-project/user wikis under `.thclaws/kms/<name>/`: three layers (immutable `sources/`, LLM-authored `pages/`, human `SCHEMA.md` + auto-maintained `index.md`/`log.md`); LLM maintains via `KmsRead/Search/Write/Append/Delete` tools; `/kms ingest|lint|file-answer|maintain|reconcile`; **no embeddings — grep + read**, explicit Karpathy llm-wiki pattern; staleness cascade marks dependent pages STALE on re-ingest; Obsidian-compatible frontmatter [tm:kms §1–4].
- **Memory** = `MEMORY.md` index + frontmatter'd entry files (`user`/`feedback`/`project`/`reference`), auto-loaded into the system prompt (categorized index, per-entry 80-line/8-KB budget, overflow deferred to `MemoryRead`); `MemoryWrite/Append` with sandbox carve-out; directory resolution prefers project scope, falls back through Claude-Code legacy paths to user-global [tm:memory §1–5].
- **`/dream`** = a first-class operation built from existing primitives: an *embedded* AgentDef (`include_str!`, overridable by `.thclaws/agents/dream.md`) spawned as a side channel; multi-pass (survey/skip via existing digests → per-session `sess-<id>` digests → canonical topic pages → reconciliation → run summary in a `dreams` KMS); tight tool whitelist (no Bash/network/recursion); review pattern is `git diff .thclaws/kms/`, not modal approval [tm:dream §1–2]. Same "memory as reviewable files, consolidation as background op" doctrine as OpenClaw's dreaming and nanobot's Consolidator→Dream — three independent implementations (map core gap #1 now has a 4th).

### 6. Scheduling / daemon / background loops (D9)
- Three independently shippable layers over one fire primitive: (1) store + `schedule run` (external cron can drive); (2) in-process scheduler — 30 s tokio tick while any surface is open, per-schedule cursors, skip-overlap guard; (3) `thclaws daemon` — PID-file lifecycle, supervised via **launchd/systemd-user** (installer emits plist/unit), plus debounced filesystem watchers (`watchWorkspace`) [tm:schedule §1–6].
- Every fire spawns `thclaws --print <prompt>` with the schedule's `cwd` (so settings/sandbox/memory/MCP scope identically), per-fire logs, timeout kill, `lastRun`/`lastExit` written back; `--resume-session last` heartbeats rehydrate provider session ids [tm:schedule §4; running-modes §1]. Schedules = 5-field cron, user-level `schedules.json`.
- Session-scoped loops: `/loop` fixed-interval iteration, `/goal` audit-driven completion with `UpdateGoal` tool and `--auto` "Ralph-style overnight builder" [tm:loop-and-goal]; `/research` background pipeline [tm:research].

### 7. Messaging / channel adapters (D10)
- **Telegram ships direct**: `getUpdates` long-poll behind NAT (no relay, no third party in path); backlog drain, offset cursor, stall guard via 55 s HTTP timeout > 45 s poll hold; inline-keyboard approval (`allow`/`always`/`deny` callback_data state machine), 6-digit CSPRNG pairing codes (1 h, in-memory), DM/group allowlist policies; Tier 1 routes all authorized chats into **one shared session** — no per-chat agent isolation [tm:telegram-bridge].
- **LINE and Messenger ship via relay** (webhook-only platforms): a server component (`line.thclaws.ai`, workspace-only crate holding Meta/LINE credentials) demuxes webhook events to per-Page WebSocket subscribers; desktop holds only a binding JWT (revocable server-side); Messenger replies carry quick-reply approval buttons; 24 h messaging-window constraints documented [tm:messenger-bridge, line-bridge]. Discord/Slack/WhatsApp are help-wanted (README) — the v1.0 "multi-platform agent" thesis.
- Adapters are surfaces of the same engine: GUI-integrated (`ShellInput::TelegramMessage` drives the worker turn; permission mode swaps to a channel-gated variant) or headless standalone loops (`--telegram`/`--messenger`).

### 8. Filesystem sandbox & approval model (D13)
- **Sandbox = in-process path validation only**: root pinned at boot to cwd (or `THCLAWS_PROJECT_ROOT` for worktree teammates, re-init on directory change); `check`/`check_write` lexical-normalize then canonicalize (new-file paths anchored at longest existing ancestor); **`.thclaws/` write-policy** reserves team/state dirs from generic Write/Edit/Bash, with per-tool carve-outs (`TodoWrite`, `KmsWrite/Append`, `MemoryWrite/Append`) each enforcing their own path-safety rules [tm:app-architecture §8; permissions §7]. No OS confinement, no read-only/danger modes.
- **Approval**: three `PermissionMode`s (Auto/Ask/Plan; Plan blocks mutating tools via an 8-layer dispatch gate incl. plan-approval-window); per-tool `requires_approval` matrix (Bash/Write/Edit/Office-create/WebFetch/MCP-any/Task/team-spawn = true; read-only = false); `ApprovalSink` trait with `Allow`/`AllowForSession`/`Deny` — **AllowForSession is a real session-scoped grant** ("yolo" in REPL), a deliberate contrast to DSH's allowed-once-only stance [tm:permissions §2–5]. Subagent approval propagation fixed in M6.20 (child inherits parent's gate, never silently auto). Three layers fail closed independently (approval / sandbox / org policy) [tm:permissions §1].
- **EE policy**: Ed25519-signed org-policy file, build-time-embedded verify key; URL allowlists gate skill/plugin/MCP installs; unverified/expired policy ⇒ **refuses to start** [tm:permissions §1; ENTERPRISE.md].

### 9. Credentials: OS keychain (D14)
- `secrets.rs`: keyring crate v3 (apple-native / windows-native / Secret Service), service `thclaws` — **keys never in settings.json**; `load_into_env()` at process start makes `std::env::var` uniform; precedence env > keychain > `.env` (dotenv fallback for CI/headless); serve mode auto-disables keychain; MCP OAuth tokens in `0600` `oauth_tokens.json` with AS-origin binding [source spot-check `Cargo.toml`/`secrets.rs`; tm:app-architecture §10; tm:mcp §3.3].

### 10. JSONL session persistence (D15)
- One append-only `<id>.jsonl` per session under `.thclaws/sessions/`; event kinds: `header`/`user`/`assistant`/`rename`/`plan_snapshot`/`compaction`/`provider_state`; `load_from` replays sequentially; **compaction events are replay checkpoints that keep the original lines on disk forever** ("audit trail"); `provider_state` rehydrates Anthropic Agent-SDK server-side session ids on resume; per-line salvage on corruption (M6.19); cross-process locking; recency-sorting deliberately excludes non-activity events [tm:sessions §1–3]. `/load` auto-switches to the session's model; `/fork` exists. Plain JSONL — no checksums/compression, no SQLite option, no projections cache.

### 11. Document / artifact tooling (D18)
- 12 office-format tools (`Docx/Xlsx/Pptx/Pdf` × Create/Edit/Read + `EpubCreate`), all sandbox-gated, `spawn_blocking` for sync crates, **per-run script-aware Thai font selection** as a first-class design constraint (bundled Noto Sans Thai; OOXML `cs` run-font ranges; per-codepoint PDF switching) [tm:document-tools §1–2]. Media tools (`TextToImage`/`ImageToVideo`/…, async jobs) + point-and-click Media Studio GUI shell (README, v0.61-era). Job Artifacts: `collect_files` declarations with **snapshot atomicity** + read endpoints + input upload API [tm:job-artifacts]. FilmScript: a purity-contracted `.film` DSL with two-phase compiler and cost/budget gate [tm:filmscript].

### 12. Deployment model (D17)
- Prebuilt binaries for 6 platform targets (incl. Windows ARM); Docker single image (`--serve` only, `--bind 0.0.0.0` inside); systemd template units (`thclaws@<project>.service`) — one process per project; SSH-tunnel trust model (loopback bind; "anyone who reaches the socket has full agent access"); **multi-tenant `--serve` Tier 1**: N users per pod via HMAC-signed `X-Thclaws-User` routing headers, per-user `SharedSessionHandle`s/JSONLs/usage under `.thclaws/users/<id>/`, LRU+idle eviction, file-asset HMAC, metering ingest [tm:serve-mode §3,6; multi-tenant-serve; docker]. Commercial layer: EE signed-policy binaries via MDM, thclaws.cloud catalog client, Agentic Press hosting with deploy-as-plugin (hosts swappable) [ENTERPRISE.md; tm:thclaws-cloud-client; README].

### 13. Structural read against DSH's five pillars
- **Cordis plugin tree vs single crate**: thClaws has no runtime composition at all — extension is directory conventions + slash commands over fixed subsystems; nothing is swappable (one session log format, one sandbox, one loop). Consequence: capability parity arrives as *shipping code*, not as mountable rows; the marketplace distributes content (skills/plugins/MCP configs), never host code.
- **Append-only session log**: both bet on JSONL-as-truth; DSH's is a typed event map with runtime invariants and surface-op semantics; thClaws's is a coarser replay format whose "checkpoint that preserves history" compaction event is the same instinct as DSH's shadowed-span replacement, minus the invariant enforcement. Notably thClaws *reads* its log as a knowledge source (`/dream` mines `.thclaws/sessions/*.jsonl`) — the log as corpus, a use DSH's trajectory view gestures at but no shipped consumer performs.
- **Capability seams vs subsystem modules**: thClaws's swappable units are the `Provider` trait (25 fixed variants, compiler-enforced exhaustive dispatch) and `ApprovalSink` (five impls incl. chat-channel approvers); everything else is a module. The chat-approver sinks are the sharpest seam idea: approval UI as a pluggable per-channel surface.
- **Sandboxing**: sharpest asymmetry — DSH confines at the OS (bwrap/Landlock/Seatbelt/ACL runners, fail-closed) with in-process freshness guards; thClaws validates paths in-process with carve-outs and no network story (net_guard.rs exists, 5 KB, unexamined). thClaws's `.thclaws/`-reserve + per-tool carve-out pattern is nonetheless a clean answer to "where does agent-maintained state live" that DSH answers with scoped realms.
- **Client/server**: both loopback-first with the browser as thin renderer; DSH's browser is a plugin roster with slots (extensible), thClaws's is one closed single-file React app shared desktop/web (uniform, not extensible). thClaws's `handle_ipc -> bool` shared-dispatch invariant is the mechanism that made one frontend serve two transports — the pragmatic mirror of DSH's typed RPC gateway.
