01Five words you need, then everything reads itself

Every finding in the map is a comparison against DSH, built from these five base labels. Two extensions keep the table readable: where a dimension splits between calls, the column shows a split call marker or simply the sub-call chips side by side; and a few rows carry variant chips — plugin-demonstrated, marketplace covered, DSH leads — that refine a base label to a narrower context, or record where DSH itself leads. This is the whole vocabulary — the rest of the report just applies it.

Equivalent DSH already does this (maybe by a different mechanism). Nothing to do.
Packaging gap No new capability code. Everything needed already ships inside DSH — the missing work is assembly: config, a bundle/preset, a shell around existing parts. Cheap, low-risk.
Plugin opportunity New code required — but it bolts onto an existing seam (the map names it). The kernel itself doesn't change.
Core gap Needs runtime/host substrate DSH doesn't have. Real architectural decisions, not a weekend plugin.
Not applicable A deliberate philosophy difference or someone else's SaaS — interesting, not a gap.
Source chips: plain chips name a cohort harness. The purple-bordered variant appears in two distinct senses — in the cohort (§02) it marks the two post-synthesis joiners; in the gap and opportunity cards it marks a DSH-ecosystem plugin, where the evidence for the call lives in the ecosystem rather than the cohort.
One more distinction the map is strict about: capability (what the user/agent can do) vs mechanism (how the code does it). Two harnesses can be Equivalent on a capability while implementing it completely differently — that difference is recorded, but it doesn't change the label.

Yes, plugins ship as packages — so what separates the two "gap" labels? The container isn't the axis; whether new capability logic must be written is. Quick test: can it be built with config/composition over what already exists? → Packaging gap. Does it need a new package containing new logic, attaching at an existing seam? → Plugin opportunity. Is there no seam to attach to at all? → Core gap. Example pair: a public generated client SDK packages DSH's existing typed gateway for outside consumers (composition over shipped parts), while an LLM approval layer requires writing actual judge/reviewer logic as a new tools/pre-execute plugin (new code, existing seam).

The 60-second version

  1. DSH's architectural bets are winning. Event-log-as-truth, Code Mode, goal models, bounded-context discipline, typed client protocols — taken as a set, the biggest players (Codex, OpenHands, OpenCode, Claude Code) independently re-derived each of them. You built what the industry is converging on.
  2. The composition kernel is still unique. No other harness in the cohort has DSH's "everything is a plugin, swapped at runtime through typed seams" core. Pi's in-flight rewrite is the closest independent parallel. This is DSH's differentiator, not a liability.
  3. Five true core gaps survive review (memory was promoted to plugin territory after the owner's ecosystem audit — see below): network-egress policy, an always-on host substrate (narrowed by an existing cron plugin), live remote sessions, interactive desktop control, multi-device orchestration.
  4. Cheapest high-value move: an LLM approval/review layer. Five harnesses built one independently; in DSH it fits the existing tools/pre-execute + ctx.approval seams with zero core changes — and no plugin in the registry does it yet.
  5. The DSH plugin ecosystem already covers several "gaps" the map first scored against the core repo: cross-session memory (mnemon ★532, dsh-memory-connect…), marketplaces (awesome-deepseek-harness-plugins ★197 indexing 11,000+ plugins), desktop shells (dshcode ★445), scheduled session firing (dsh-timer-agent). For a composition kernel, ecosystem coverage is capability — the map now scores it that way.
  6. Everything moves. Every claim is pinned to a dated snapshot; several repos rewrite weekly. Re-pin before quoting. (Cline even removed its browser tool mid-migration during our profiling window.)

05Packaging gaps — four survive review; two are ecosystem-covered

Capability exists as shipped parts; the composed product doesn't. These are the "assemble the LEGO" tickets.

Plugin marketplace ecosystem-covered

Owner review: ≥7 marketplaces already exist — awesome-deepseek-harness-plugins ★197 (11,000+ plugins, free search API), dsh-plugin-panel (in-app store), dsh-unified-market, dsh-plugin-recommend. No first-party marketplace (per the #31 live-page finding), but that's an unowned surface, not a gap.

Desktop / native distribution ecosystem-covered

Owner review confirmed: dshcode ★445 (one-click Electron, macOS/Windows), multiple dsh-desktop variants (Wails cross-platform, WebView2 with tray + auto-start, server-supervising shells). Community coverage is strong; nothing first-party.

Public client SDK

Codex generates TS/JSON schemas from its app-server; OpenCode publishes OpenAPI 3.1. DSH's typed gateway is private. packaging

Stock toolkits & personas

Eigent's ~40 toolkits / 8 personas, OpenCode's agent presets, nanobot's persona files — all composable in DSH today, none composed. packaging

Provider onboarding & keyring

Subscription OAuth flows (Cline, Claude Code, goose, OpenCode) and OS keyring storage — friction removers, not capabilities. packaging

Trace/debug tooling

Codex's opt-in raw-trace → semantic-graph reducer is the model: DSH has the log, not the debugger UX. packaging

Not applicable (not gaps): SaaS credits/billing backends (Eigent, CC, Codex cloud) · research protocol stacks (UFO³ AIP) · framework doctrines (OpenCode's Effect vs Cordis) · fork-and-white-label distribution (goose) · directory-scan extension (nanobot, Agent Zero) · Cline's Memory Bank convention.

The ecosystem already has edges into (and around) DSH

Solid purple = dependencies into DSH (it already wraps pi-ai and routes Codex search). Dashed gray = ecosystem flows: Claude Code's formats spreading, OIX forking Codex's app-server, goose importing other harnesses' sessions. The map is not cycle-free — DSH is already a participant, not just an observer.

The minimalism reveal (nanobot): channels + memory + cron + persona turn out to be "files plus one bus" in the leanest harnesses. The expensive part of those capabilities is not the capability — it's the always-on host. That asymmetry should shape the order of any DSH roadmap.

08What's still open

Re-pin before quoting

Fast movers: Codex (daily), OpenCode (V2 rewrite), Cline (mid-migration), OpenClaw channels, Hermes (~daily), OpenWorker (beta), Cloudflare OS (early access).

Baseline questions

Does a DSH TUI exist? Which event dispatch mode is real (parallel vs bail)? Is any shipped bundle schedule-enabled? Can checkpoints be complete when shell effects bypass fs/write-intent?

Security posture questions

DSH's plain-HTTP webServer seam needs an origin-policy stance before channel plugins. thClaws' net_guard.rs/confine.rs remain unread; do not revise the 3/19 D13 count until targeted verification shows that they gate egress.
