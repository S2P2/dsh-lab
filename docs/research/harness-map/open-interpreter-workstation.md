# Open Interpreter + Interpreter Workstation: architecture & distinctive capabilities

**Verdict.** Open Interpreter and Interpreter Workstation are the field's cleanest two-process separation of *agent runtime* from *desktop UX*: the runtime — `openinterpreter/openinterpreter`, "OIX", a fork of OpenAI Codex rewritten in Rust — owns the agent loop, sandboxing, providers, skills, sessions, and a JSON-RPC **app-server protocol** (Codex-inherited, extended with an `interpreter/*` namespace); Workstation — `openinterpreter/interpreter-workstation`, an Electron app — owns the shell, overlay, permissions UI, workstation tools, browser bridge, and computer-use driver, and reaches the runtime *only* through that protocol plus the `interpreter-app` CLI contract for model-facing app tools. Two OIX decisions are materially novel vs DSH: (1) **harness emulation** — one runtime re-implements the model-facing surface (prompt, tool schemas, message conversion, request shaping) of Claude Code, Kimi Code, Qwen Code, GLM/ZCode, DeepSeek TUI, SWE-agent and more, selected per thread and auto-inferred from provider family, explicitly to get "the best performance out of low-cost models"; (2) **portability as an engineering constraint** — shared `AGENTS.md`/`.agents/skills`/MCP/ACP/Codex-exec surfaces instead of product-owned formats, with `~/.openinterpreter` reserved for state that has no shared standard. DSH's orthogonal move is composition (everything a swappable plugin over one event-sourced log); OIX's is protocol compatibility (be the drop-in binary for other agents' clients while re-shaping the harness surface above any provider). Workstation's distinctive surface — desktop computer use, overlay-first UX, per-agent file scopes, structured session grants, voice — is almost entirely DSH D12/D10-absent territory, i.e., where the map's "absence is data" cuts in DSH's disfavor.

## 1. Identification & the runtime/UX split (verified)

- **Ticket's ID confirmed with a twist.** `OpenInterpreter/open-interpreter` now redirects to `openinterpreter/openinterpreter` — the repo was rewritten from Python to a **Rust fork of OpenAI Codex** (crates `codex-rs/*`, `codex-core`, `codex-tui`; `FORK_BRANDING.md` documents inherited internal names vs product identity, `Product::current()` in `codex-rs/product-info`). README: "a fork of OpenAI's Codex, with a focus on emulating the agent harness that gets the best performance out of low-cost models." Apache-2.0. Install `curl …/install | sh`; commands `interpreter`/`i`.
- **Split contract (Workstation README §Architecture, WS AGENTS.md §Product boundaries):** OIX owns agent runtime, harnesses, provider/model discovery, app-server protocol. Workstation owns Electron shell, UX, local policy, workstation tools. "The desktop app does not maintain a second provider or harness implementation." Model-facing app tools ride the **`interpreter-app` CLI contract** only ("Do not add a second direct model-facing tool surface"); app turns start with `mcp_servers: {}` (overlay-architecture.md §Tool surface).
- **Versioning decoupling:** Workstation launches its exact checksummed OIX pin while the terminal's `interpreter` follows an independently movable `current` selector — "a terminal update cannot change the app-server protocol underneath a released Workstation build" (README §OIX runtime; oix-local-testing.md). Both share one home `INTERPRETER_HOME`/`~/.openinterpreter` (config, sessions, plugins, skills) with a two-owner managed-skills contract: Workstation manages its shipped skills (hash manifest, backup-before-replace, staged updates), OIX owns `skills/.system/` exclusively (skills.md WS + OIX).

## 2. Architecture profile, by question area

**Agent runtime vs desktop UX.** OIX is a monolithic-ish Rust workspace (~130 crates: `core`, `tui`, `app-server`, `exec`, `acp-server`, `sandboxing`, `linux-sandbox`, `windows-sandbox-rs`, `skills`, `memories`, `plugin`, `hooks`, `code-mode*`, `model-provider-info`, `rollout`, `thread-store`…) — extension is config (TOML), skills, MCP, hooks, experimental plugins; *not* everything-is-a-plugin. Workstation is React/Electron + an Express "server/" backend that itself runs headless (`server/standalone.ts`: sidecar or one-shot `--message --shutdown-after-task`), so even the UX layer is split into headless-server + renderer. IPC doc mandates ONE business-logic implementation in `server/handlers/*`, thin Electron-IPC and HTTP routers over it, and a hard trust tier: **privileged desktop capabilities (arbitrary local file R/W, thumbnails, shell integration) must never be mirrored onto loopback HTTP** — a boundary DSH (plain `node:http`, no auth, deliberate) deliberately does not draw.

**Permissions.** Two independent OIX axes: `sandbox_mode` (`read-only`/`workspace-write`/`danger-full-access` — DSH's exact triad) × `approval_policy` (`untrusted`/`on-request`/`never`), plus newer **permission profiles**: named TOML profiles with filesystem globs (`read`/`write`/`deny`, deny wins, roots `:minimal`/`:workspace_roots`/`:tmpdir`/`~`/abs), **network domain allow/deny globs** (`*.example.com`, `**.`, exact; private/local guarded separately), and **unix-socket rules** (docker.sock). OS enforcement = Seatbelt/bwrap+seccomp/Windows-native, fail-closed (sandbox.md). Workstation adds a per-agent layer: global policy → `GlobalFileAccessResolver` → `filesystemBoundary` auto-checks on every tool (`fileAccess` declared per tool; scopes Sandbox > Custom paths (blacklist!) > Workspace > System), "per-agent permissions narrow the global ceiling, never broaden" (overlay-architecture.md §Permissions). Approvals: single `ApprovalManager` queue, one `QuestionRequest` card model, canonical structured session-grant key `{v, ownerId, sourceKind, serverId, capabilityId, workspacePath, windowSessionKey, targetScope}`; consent cards visually/behaviorally distinct from display cards; `computer_batch` review is a separate surface from native approval; `execCommandApproval` arrives as an app-server server→client request.

**Workstation tools.** Builtins + MCP servers discovered/called through `interpreter-app tools …`; `ToolManager.callTool()` is the single choke point; `js_repl` = persistent Node kernel in the Express backend (`server/tools/builtin-tools/js-repl/`, bundles `playwright-core`); `read_image` routes a local file through the profile's vision model; large outputs (>20k chars) spill to sandbox files. Terminal-tab agents get an HTTP MCP endpoint `/mcp/:profileId/:tabId` executing tools immediately.

**Browser / computer / file execution.** OIX itself: QA skill driving web via `agent-browser` or native apps via `trycua` (README §Computer Use). Workstation: pinned **interpreter-cua** driver (thin TryCua fork; only privacy no-op edits + additive window tools allowed, patch inventory verified pre-merge) behind macOS AX / Windows UIA; pinned **interpreter-extension** (Playwriter fork) relay on `127.0.0.1:19988`, extension-icon-per-tab consent, Playwright-over-CDP for arbitrary pages; unified computer catalog + `computer_batch` envelope (strict pre-validation; per-action results + **before/after window DIFFs, never full dumps**); refs are current-observation handles that fail loudly when stale; loose JSON from fast models → mechanical normalization then schema-validated **fast-repair model**, never blind execution; denial-parity rule (policy denial binds the target, not the transport — no CDP fallback bypass). File execution additionally flows through document workflows = code execution + Apache-2.0 skills (python-docx/pypdf/pptx/openpyxl), optional external document engine (OO Editors) as a lazily-started local protocol (port 38123) — never a bundled proprietary SDK.

**Sessions.** OIX: local sessions under `~/.openinterpreter` (rollout store); `interpreter resume|fork` (CLI picker, `--last`, `--all`), `/fork` `/side` in TUI, exec sessions resumable; `/compact` + auto-compact near context limit; history `persistence="none"` / `max_bytes` caps. Protocol surface: `thread/start|resume|name/set|archive|read|list`, `turn/start|steer|interrupt`, notifications `turn/plan/updated`, `thread/compacted`. Workstation keeps threads in OIX; app-side adds agent tabs (`agentTabManager`), tabs-as-context (`POST /api/agent/context/tabs`), checkpoint handler.

**Model/provider handling.** OIX trichotomy (providers.md): **provider** (endpoint, credentials, `wire_api` ∈ responses/chat/messages) × **model** × **harness** (agent-facing prompt/tools/shaping). `/model` and `/harness` TUI pickers; automatic harness defaults inferred from provider family (Anthropic→`claude-code`, Kimi→`kimi-code`, Qwen→`qwen-code`, **DeepSeek→`claude-code-bare`**); strict route compatibility (Messages transport *requires* a harness); built-in runtime providers + generated hosted catalog (`provider_catalog.json`). App-server extensions `interpreter/provider|model|harness/list|set` (protocol.ts). Workstation consumes the list methods, passes provider/model/harness **as per-thread config**, never mutating OIX's global selection — concurrent agents stay independently configurable; `harness: null` = explicit native Codex, omitted = Automatic. Local models: Ollama/LM Studio integration tests ship in Workstation; profiles = provider+model+credentials picked at first launch.

**Remote / client-server.** OIX: `interpreter app-server --listen stdio://|ws://…`; optional **daemon** on a unix socket shared by several clients (`interpreter app-server daemon start|stop`); TUI attaches remotely via `interpreter --remote wss://… --remote-auth-token-env …` (bearer token; plain ws only on trusted local links). Protocol is deliberately **Codex-app-server-compatible** so existing Codex clients can launch `interpreter` instead (app-server.md) — and the Codex JS SDK works with a one-line `codexPathOverride: "interpreter"` (README). ACP: `interpreter acp` for ACP editors. Workstation: Electron-local by default, but `server/standalone.ts` gives a headless sidecar; product.json carries `serverApplicationName`/`tunnelApplicationName` identities (tunnel service mutex names) — ⚠ evidence of a designed remote/tunnel story beyond shipped docs.

### 3.1 Boundary lessons (material differences, distilled for synthesis)

1. **Protocol identity as a feature.** OIX treats *being compatible with other agents' protocols* (Codex app-server, Codex exec/SDK, ACP, MCP, AGENTS.md, `.agents/skills`) as the product surface; DSH treats *its own composition seams* as the surface. Neither approach subsumes the other: DSH cannot be dropped into a Codex SDK client today; OIX cannot swap its loop driver or sandbox provider without a Rust change.
2. **Two kinds of "preset."** DSH per-session presets swap *composition* (which tools/persona); OIX harnesses swap *model-facing shape* (prompt + tool schemas + message conversion + request shaping per emulated product, auto-selected per provider family). The strongest plugin-opportunity signal in this profile: harness-shaped presets for low-cost models, built on DSH's existing preset + `ctx.llm` seams.
3. **Privileged-client tier.** Workstation splits capabilities into shared (HTTP-safe) vs privileged (trusted-renderer-only, never mirrored to loopback HTTP) with typed preload bindings as the enforcement point. DSH's web carrier is deliberately plain and unauthenticated; nothing in DSH distinguishes "safe to expose over HTTP" from "renderer-only."
4. **Permissions as data, not mode.** OIX permission profiles (fs globs + network domain globs + unix sockets, deny-wins) and WS structured session grants (owner+capability+target-scope, never broaden) are both *declarative, inspectable policy objects*; DSH's equivalents are runtime modes + one-shot approvals. DSH has the seams (`ctx.approval`, `ctx.sandbox`) but no policy-document layer.
5. **Computer use with a denial-parity rule.** WS's CUA stack enforces that a policy denial binds the *target* (browser page denied ⇒ AX/screenshot reads of the same target also refuse), so fallback transports can't bypass policy — the single most portable security idea in the profile for any future DSH D12 work.
6. **Version-pinned runtime under a moving terminal.** App-pinned checksummed runtime + independently movable terminal selector + shared home with two-owner managed-skills is a concrete answer to "how do a GUI and CLI share one agent installation without coupling release cadence" — directly comparable to DSH profiles sharing `$DSH_HOME`.

## 4. Uncertainties / open questions

1. **⚠ Crate-level claims** (`code-mode*`, `v8-poc`, `agent-graph-store`, `collaboration-mode-templates`, `memories` internals, otel/rollout-trace) rest on crate names + doc skims, not source reads — the OIX repo is huge and Codex-inherited; some crates may be upstream vestige rather than shipped OIX surface. Verify `code-mode` vs DSH Code Mode before charting as parallel evolution.
2. **Desktop docs site crawled via search index only** (pwsh/curl TLS blocked); voice-mode details (qwen-asr local install, realtime transport) come from WS repo scripts/tests + one crawled install page. The separate website repo was not inspected.
3. **Tunnel/server identities** (`interpreter-tunnel`, `interpreter-server` in product.json) suggest a remote-access story I found no doc for — possibly unreleased or VS Code-lineage vestige (the product.json schema is visibly derived from a VS Code fork).
4. **`rust-v0.0.34` pin vs HEAD**: Workstation pins a release tag, not the OIX `main` I profiled (@5b07159); app-server surface may differ slightly between the shipped pin and main. The `interpreter/*` protocol methods were read from WS's client, which tracks the pin — safer than OIX main docs.
5. **Legacy Python Open Interpreter** (0.4.3: `--os` Computer API, server mode with `INTERPRETER_REQUIRE_AUTH` env vars per third-party guide PDFs) treated as lineage only; if the map wants the historical profile, that's a separate dig.
6. **Workstation "automaticProfiles"/persona derivation** (`server/derivePersona.ts`, `handlers/automaticProfiles.ts`) — name-level only; how per-agent personas compose with harness personas unread.
