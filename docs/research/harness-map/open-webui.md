# Open WebUI profile: capability surface vs the DSH baseline

**Verdict.** Open WebUI is the cohort's **multi-user, self-hosted LLM workspace platform** — a FastAPI monolith + SvelteKit SPA product (formerly Ollama WebUI) that has, by this HEAD, grown *inward* from "chat UI over model servers" toward an agent harness: a bounded native-function-calling loop (default 256 iterations), a builtin tool catalog with memory/notes/calendar/delegation tools, RRULE scheduled automations that run chats autonomously into team channels, a proxied external terminal-server exec surface, and an MCP client bridge. But its center of gravity remains **platform, not harness**: every capability is a row in a single-tenant (one organization) multi-user server with role/group permission checks on every path, DB-stored chats/knowledge/skills, and extension by *DB-stored Python snippets* (Tools/Functions/Filters with Valves) plus external tool/terminal/MCP servers — there is no composition kernel, no plugin dependency graph, no per-session runtime isolation. Its distinctive strengths vs DSH are exactly the platform dimensions DSH records as absent: durable multi-user RBAC + group-scoped resource grants, per-user agentic memory with its own tool surface, scheduled autonomous agents with run history, chat-platform-ish Channels for human↔agent collaboration, and an operations story (auth/SCIM/OAuth, horizontal-scale knobs, OTel). The loop/session/permission *interior* is comparatively thin: no event-sourced log, no admission control, no approval waterfall beyond a two-mode per-message tool gate, no fork/resume, no subagent isolation (children inherit parent's tools/model wholesale).

Category call (UFO³-style caveat): Open WebUI is **not a single-operator agent harness**; it is a server product whose "session" is a *user's saved chat*, whose "extension" is *DB rows + external HTTP servers*, and whose "agent" is a *chat completion pipeline*. D1/D2/D15 dimensions partially have no room to map; recorded as absent rather than stretched. Like Cloudflare OS (the cohort's other multi-user profile), multi-user sharing/RBAC is where it diverges most from the single-operator harnesses — but unlike CFOS it is self-hostable anywhere (Docker/pip) and database-portable, not platform-bound.

## 2. Architecture profile

### 2.1 Server/client architecture

- **Single FastAPI monolith** (`backend/open_webui/main.py`, ~3k lines): ~31 `include_router` API domains (`/api/v1/{chats,channels,notes,memories,skills,knowledge,tools,functions,groups,users,auths,files,folders,prompts,automations,calendars,terminals,notifications,analytics,evaluations,scim/v2,…}` + `/ollama` + `/openai` compat APIs), socket.io app mounted at `/ws`, static SPA mount at `/` (`main.py:817–864,2984` @ `d3e8bf3`).
- **Async SQLAlchemy 2.0 + Alembic** persistence (`pyproject`: `sqlalchemy[asyncio]`, `aiosqlite`, `psycopg`; `migrations/`), Redis for multi-worker socket.io pub/sub + session/task pools (`starsessions[redis]`, `redis==8.0.1`; `main.py:387–390` lifespan starts `redis_task_command_listener`, periodic pool cleanups).
- **Lifespan background workers** (`main.py:339–394`): license fetch, redis task-command listener, periodic usage/session pool cleanup, and `scheduler_worker_loop` (automations, §2.7).
- Frontend: SvelteKit SPA (`src/`); server streams chat via socket.io events (`chat:completion` output items, Responses-API-shaped `output` arrays — `utils/middleware.py:3341–3367`).
- No microservices in-core; scaling out = multiple uvicorn workers against shared Postgres + Redis (`docker-compose.api.yaml`, `WEBUI_SECRET_KEY`, `ENABLE_WEBSOCKET_MANAGER`-family envs @ `env.py`).

### 2.2 Model/provider routing (connections)

- Three model planes merged into one `app.state.MODELS` registry: **Ollama** (`routers/ollama.py`), **OpenAI-compatible** (`routers/openai.py`), and **Pipe functions** (DB-defined Python "models", `functions.py:153` `generate_function_chat_completion`). Admin "connections" + per-user **Direct Connections** (BYO provider keys client-side) merge into the model list.
- Direct provider SDKs shipped: `openai`, `anthropic`, `google-genai` (`pyproject.toml`); plus **Arena models** — wrappers that pick a random sub-model per request, excludable list (`middleware.py:2374–2398`).
- A **task model** (separate cheap model) handles titling, tag/autocomplete, follow-up generation, retrieval query generation (`routers/tasks.py`; `utils/task.py`).
- Per-model config lives in `models.meta` JSON (params, knowledge, skillIds, capabilities flags like `builtin_tools`, `terminal`, `file_context`, `citations` — e.g. `middleware.py:2767,2928,3043`); model records are DB rows users can clone/customize ("custom models").

### 2.3 Tools / functions / pipelines — the chat pipeline and agent loop

- **Pre-model pipeline** (ordered, `process_chat_payload` `middleware.py:2362–3105`): Pipeline inlet → Filter inlets (DB Python filters) → chat memory context → web search (legacy mode) → image gen (legacy) → code-interpreter prompt (legacy) → skill resolution → tool resolution (DB tools + MCP servers + terminal servers + direct client tool servers + builtins) → file/RAG context injection → system-message merge. The doc comment at `middleware.py:2367–2369` states this order verbatim.
- **Two function-calling modes**: `native` (default — tools passed as OpenAI `tools=[…]`, loop below) vs `legacy` (prompt-injected XML-ish tags + `chat_completion_tools_handler` parsing, `middleware.py:1278`). Legacy mode is how filters historically injected behavior (web search/image gen as pre-stages).
- **Bounded agent loop**: `while tool_calls and iterations < max` — default **256 iterations** (`CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS`, `env.py:1062–1077`; 0 ⇒ unlimited), executes tool calls, appends `function_call`/`function_call_output` items to the message's persisted `output`, reloads full history from DB, re-calls `generate_chat_completion` (`middleware.py:5502–5988`). Output items follow a **Responses-API-shaped item model** (`message`, `reasoning`, `function_call`, `function_call_output`) stored on the chat row (`Chats.upsert_message_to_chat_by_id_and_message_id`, `middleware.py:3352`).
- **Tool gate**: `tool_approval_mode: 'full' | 'ask'` — in `ask` mode every non-`ask_user` call is persisted `pending`/`queued` and the turn **pauses** (chat stays resumable); approval later resumes via `drain_approved_tool_calls` → `pause_for_tool_approval` (`middleware.py:3226–3455`). `ask_user` itself pauses for interactive answers (`stage_ask_user_tool_call`, `middleware.py:5533–5548`).
- **Builtin tool catalog** (`tools/builtin.py`, ~60 tools, injected only for UI-originated requests with native FC, `middleware.py:2976–3018`): `search_web`, `fetch_url`, `generate_image`/`edit_image`, `ask_user`, `execute_code`, **memory suite** (list/read/search/add/update/replace/delete), **notes suite** (CRUD + grep), `search_chats`/`view_chat`, `search_channels`/messages/threads, **knowledge suites** (list/search/query/grep/view knowledge bases + files), `delegate_task`, `timer`, **tasks CRUD**, **automations CRUD**, **calendar CRUD**, chat-file grep/query. Tools are plain async functions with `__user__`/`__request__`/`__event_emitter__` injected params; spec = parsed docstring → Pydantic model (`utils/tools.py:805–1005`).
- **Code interpreter**: `execute_code` engine `pyodide` (default) runs **in the browser** via socket.io event call `execute:python` — the server only sanitizes + prepends an import blocklist shim (`tools/builtin.py:621–780`); `jupyter` engine proxies an external Jupyter server (config `code_interpreter.jupyter.*`). RestrictedPython is a declared dep but unused at this HEAD (no import found — vestigial).
- **Functions/Filters/Pipes** = DB-stored Python modules dynamically imported, each optionally with `Valves` (admin) and `UserValves` (per-user) config classes (`functions.py:52–211`); filters run `inlet`/`outlet`, pipes implement whole models, `action` functions react to events. Enabled via `ENABLE_PLUGINS`.
- **Pipelines** (`routers/pipelines.py`): proxy to the separate `open-webui/pipelines` service — externally-hosted function hosting for scale-out (designated URL per pipeline "model"; not bundled).

### 2.4 MCP & external tool protocols

- **MCP client bridge**: admin-configured connections (`tool_server.connections` entries `type: 'mcp'`), per-user/group access-checked, **streamable-HTTP transport only** (no stdio — `utils/mcp/client.py` uses `streamablehttp_client` exclusively), per-request connect → `list_tools` → bridge each tool as `<server_id>_<name>` native-FC tool → disconnect in a response finalizer (`middleware.py:2311–2360,2854–2906,1697–1719`). Optional tool-name filter list per connection.
- **MCP OAuth**: dynamic client registration + token refresh for MCP tool servers (`main.py:609–632`, re-registration at `main.py:2659`); client class exposes `list_resources`/`read_resource` but no caller surfaces them to models at this HEAD (client-only capability, unused).
- **OpenAPI tool servers**: admin or per-chat "direct tool servers" — OpenAPI specs converted to tool payloads (`convert_openapi_to_tool_payload`, `utils/tools.py:1071`), called via `execute_tool_server` HTTP; **terminals** are a third protocol: reverse-proxied terminal servers exposing `run_command`/file tools with cwd tracking (§2.9).
### 2.5 Knowledge / RAG / memory

- **Knowledge bases**: DB "knowledge" collections (files chunked + embedded into a vector DB) attachable to models, chats, folders, notes; native-FC mode advertises them as `<knowledge>` tags + `search_knowledge_*`/`query_knowledge_*` tools instead of pre-injecting RAG context (`middleware.py:2984–3018`); legacy mode pre-runs retrieval (`query_doc*`) and injects citations (`apply_source_context_to_messages`).
- **Retrieval stack** (`retrieval/`): **15 vector-DB backends** (chroma, elasticsearch, milvus×2, opengauss, opensearch, oracle23ai, pgvector, pinecone, qdrant×2, s3vector, valkey, weaviate, mariadb) behind one client; hybrid search (BM25 `rank-bm25` + vector, or native-hybrid where supported) + cross-encoders/SentenceTransformers rerankers; embedding providers = local (sentence-transformers) / Ollama / OpenAI / Azure (`retrieval/utils.py` func list).
- **Web ingestion**: ~30 search providers (`retrieval/web/`) + Playwright as a server-side page-render engine (`retrieval/web/utils.py`, config `web.loader.engine`); YouTube transcript loader; `fetch_url` builtin tool reuses this.
- **Memory** (`models/memories.py`, `utils/memory.py`, `routers/memories.py`): per-user rows (`type: 'user' | 'context'`, `path`, content, meta) + a vector collection; **model-facing as a filesystem-ish tool suite** (list paths / read / search / add / update / replace / delete — `tools/builtin.py:788–1114`); optional auto-injection builds a system-message section from (a) *all* `user`-type memories (deterministic, path-ordered), (b) path-neighborhood hints, (c) k=8 semantic recall over the last ≤7 user messages (`add_memory_context`, `utils/memory.py:289–345`). Gated by per-model capability flag + per-user permission `features.memories`.

### 2.6 Multi-user / auth / permissions

- **Roles** `admin / user / pending` (`models/users.py`); signup gating, default role, JWT cookie sessions (`WEBUI_AUTH`, `WEBUI_SECRET_KEY`); API keys per user.
- **Auth stack**: password; OAuth (multi-provider, encrypted client info, per-user session cap, token-exchange for external apps, backchannel logout — `env.py:852–886`); **trusted-header auth** (email/name/groups/role headers from a reverse proxy — `env.py:787–790`); LDAP (`ldap3`); **SCIM v2** provisioning router (`routers/scim.py`).
- **Groups + permission maps**: groups carry `permissions` JSON (dotted keys like `features.memories`, `features.web_search`, `workspace model_access` — checked via `has_permission` throughout); **access grants** = per-resource ACL rows (`user|group|anyone` × `read|write` over `knowledge|model|prompt|tool|note|channel|file` — `models/access_grants.py:19–40`); builtin tools re-check the same grants per call (e.g. `tools/builtin.py:104–122`).
- Admin-plane controls: admin chat access/export flags, user webhooks toggle, task-model config, model-level capability flags per audience.

### 2.7 Background tasks / scheduling

- **Unified scheduler worker** (`utils/automations.py:205–273`): one asyncio loop (poll 10 s; multi-worker-safe via DB claim_due → execute) handles (1) **RRULE automations** — RFC-5545 recurrence + user timezone, min-interval limits, run-history table, re-gated owner permission + fresh short-lived token at each run (`execute_automation`, `automations.py:489–608`); (2) calendar event alerts; (3) one-shot chat timers (the `timer` builtin tool).
- An automation run goes **through the full chat pipeline** ("exactly like the frontend: filters, model params, knowledge/RAG, tools, DB saves, webhooks" — `automations.py:490–495`), landing as a normal chat or a **channel message** others can reply to; terminal sessions can persist a cwd across runs (`_set_terminal_cwd`).
- **Subagents** (`utils/subagents.py`): `delegate(task, context, background)` — child inherits parent's model/tools/skills/terminal wholesale (`run` dict, `subagents.py:317–330`), config caps (`max_concurrent` 20, `max_async` 20, `max_iterations` 30, `max_output` 30 KB), foreground semaphore; background delivery via **internal pending messages** (`process_pending_internal_messages`) surfaced into the parent chat. Background mode disabled for direct connections and for pyodide code-interpreter feature.
- Post-response tasks (title/tags/follow-up via task model) run as `background_tasks_handler` (`middleware.py:3612`).

### 2.8 Channels / integrations

- **Channels** (`routers/channels.py`, 75 KB): persistent multi-user rooms with membership, message threads, reactions, unread counts, file/image messages, pycrdt/`ydoc` realtime; **channel webhooks** post external events in with a synthetic `role: 'webhook'` identity (`channels.py:910–916,1821+`); automations target channels; `search_channels`/`search_channel_messages` are model tools — i.e. channels are both human team chat and an agent-readable/writable message bus.
- Outbound integrations otherwise thin in core: per-user **webhook notifications** (new-user/channel events), email notification settings; no first-party Slack/Telegram/Discord connectors — those live in the **Open WebUI Computer** product (below) or community functions.
- **OpenAI-compatible exposure**: the whole server is itself an API endpoint — `/api/models`, `/api/chat/completions` with server-side tool execution (`main.py:874,1085`; docs reference "Server-Side Tool Calling (API)"), plus `/ollama/*` and `/openai/*` compat shims.
- **Adjacent ecosystem products** (separate repos, docs `ecosystem/`): **Open Terminal** (terminal servers; enterprise-licensed per docs enterprise page: "enterprise-exclusive offerings like Terminals"), **Open WebUI Computer** (`pip install cptr` — full browser workstation: real files/editor/terminal/git, coding agents with per-chat approvals, Telegram/Discord/Slack/WhatsApp/Signal messaging bots, scheduled tasks; can appear as a model inside Open WebUI), **oikb** knowledge-base sync. Recorded as boundary, not core capability.

### 2.9 Browser / computer-use surfaces

- **None for the model in core.** No browser automation tool, no screenshot/DOM tool. Server-side Playwright exists solely as a *fetch/ingest* engine for RAG and `fetch_url` (`retrieval/web/utils.py`). Computer-use lives in the separate Computer product (coding agents that "browse the web" with approvals — docs `ecosystem/computer`). Terminal *is* core's exec surface: proxied external terminal servers exposing `run_command`/file tools, per-chat session contexts, cwd tracking, group-gated (`routers/terminals.py`; `utils/tools.py:1351–1463`) — enterprise-licensed per docs.
- `execute_code` sandbox = **browser-side Pyodide** (WASM) via socket.io event call, or external Jupyter; server-side "blocking" is a docstring-import blocklist shim, not a sandbox (`tools/builtin.py:646–694`).

### 2.10 Persistence / state

- Single primary DB: SQLite (default `./data/webui.db`) or Postgres/MySQL via `DATABASE_URL`, async SQLAlchemy + Alembic migrations (`env.py:267`, `migrations/`); ~25 tables (`models/` — chats, chat_messages, shared_chats, tags, folders, channels, notes, memories, knowledge, files, functions, tools, skills, prompts, automations, calendar, feedbacks, groups, users, oauth_sessions, access_grants, config…). `config` is per-key DB rows (admin-editable at runtime) layered over env defaults.
- Chats persist as JSON history blobs + normalized message rows; assistant "output" carries structured items (reasoning, function_call(+output), citations) replayed into later requests (`middleware.py:2409–2426,3385–3389`).
- **Attachments/files**: local disk or S3/Azure/GCS (`config.py:146–166`, `STORAGE_PROVIDER`); vector data separate per-DB; Redis optional for websocket fan-out + session pool. Export/import = full DB dump via admin (JSON zip).

### 2.11 Deployment / self-hosting

- **Artifact**: Docker image (default `:8080`, embedded Ollama variant, GPU/amd-gpu/api/data compose variants incl. `docker-compose.otel.yaml` and `docker-compose.playwright.yaml`), Kubernetes/Helm charts, `pip install open-webui` / `uvx` (`pyproject.toml`, `docker-compose*.yaml`, docs getting-started). Python 3.11/3.12 only.
- Scale-out: N uvicorn workers + `DATABASE_URL` Postgres + Redis websocket manager (`starsessions[redis]`); `docker-compose.api.yaml` is the multi-worker reference. Docs enterprise section sells "Architecture & High Availability" deployments (commercial).
- Self-migrating data dir on version change (`env.py:222–244` moves/merges old DATA_DIR); `WEBUI_SECRET_KEY` shared across replicas.

### 2.12 Observability

- **OTel built in**: traces (OTLP gRPC or HTTP + basic auth) + metrics with SQLAlchemy instrumentation (`utils/telemetry/{setup,metrics,instrumentors}.py`; `ENABLE_OTEL_TRACES/METRICS`). No chat-content-level tracing of its own — spans/metrics are HTTP/server-level.
- Admin **analytics** dashboards (model usage, counts, unique users/chats from chat_messages — `routers/analytics.py`); **feedback + Elo leaderboard** for arena-style model comparison (`routers/evaluations.py`); automations keep a run-history table (`AutomationRuns`). Per-user chat log is the audit surface (admin access gated); `events.py` publishes structured domain events (`publish_event`) consumed by action functions/socket.
- Loguru + per-source log levels (`env.py:107–127`). No first-party tracing of *tool-call provenance* beyond stored chat output items.

### 2.13 Extension/plugin mechanisms

- **Four extension rails, all DB-stored Python** (workspace "Plugins"): **Tools** (callable functions), **Filters** (inlet/outlet message transforms), **Pipes** (whole custom models), **Actions** (event reactions) — dynamically imported modules with admin `Valves` + per-user `UserValves` config schemas (`functions.py:52–211`); gated by `ENABLE_PLUGINS`; shared via community Hub (external site), imported by URL/ID. No dependency graph, no versioning, no isolation — module code runs in-server with full app state via injected `__request__`/`__user__`/`__event_emitter__`.
- **External servers** as the heavy-machinery rail: OpenAPI tool servers, MCP servers (streamable-HTTP + OAuth dynamic registration), terminal servers — admin-configured connections with group access; per-chat *direct* tool servers client-supplied.
- **Skills** = DB markdown prompt-libraries (D4) with access grants; distinct from code plugins.
- Frontend extension: none (closed SPA) — a docs "custom frontend" tutorial pattern forks the Svelte build. Contrast with DSH's browser slot/HMR plugin plane.

## 4. Absence is data (both directions)

**OWUI lacks** (DSH strengths): composition kernel (profiles/bundles/seams — config is flat env+DB rows); append-only session log with replay/fork/resume and the "model-visible means logged" invariant; admission control; guarded tool pipeline depth (deny-only guards, post-policy replace, auditable approval pairs); per-agent runtime scopes with shadowing; continuable subagent handles + isolation/depth model; workflow scripts; goal model; plan mode; repo instruction files; ACP/editor channel; client plugin plane/HMR/slots; crash recovery semantics; OS-confinement in core (exec is delegated out).

**DSH lacks** (OWUI strengths — the platform half): durable multi-user identity/RBAC/groups/ACL grants/SCIM; per-user agentic memory with tool CRUD; RRULE scheduled autonomous runs with run history; shared channels as human↔agent bus; OpenAI-compatible *serving*; 15-vector-DB RAG stack + 30 search providers + Playwright fetch; arena models + Elo leaderboard; admin analytics; enterprise licensing/HA story. (Cf. Cloudflare OS — the other multi-user profile: CFOS enforces capability security by *topology/types*, OWUI by *checklists on every route*; CFOS has no plugin ecosystem, OWUI's is DB-snippet+HTTP-servers; both lack DSH's log/composition interior.)
